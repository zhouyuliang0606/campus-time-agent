## 〇 现场事实（`admin1`，21:33:39-21:34:08 实测）

### 0.1 这一轮的原话（`app/data/student/admin1/sessions.json` 抄录，`sid=s1e63b87257`）

```
user:      删除周6所有代办

           1. 打乒乓球｜10:00–13:00
```

**两条选得对**（打乒乓球、健身房）。不对的是**形状**：说一次，出了两张卡，得点两次。

### 0.2 这两张卡是模型调工具调出来的，不是规则层

`app/data/trace_log.jsonl` 第 802 条（21:34:08，`sid=s1e63b87257`）：

```
tools: ['propose_todo_remove', 'propose_todo_remove', 'propose_todo_remove', 'propose_todo_remove']
options_n: 2
agent_mode: False
```

4 个工具名 = **2 次调用 + 2 次结果** ⇒ 模型自己调了两次 `propose_todo_remove`，一次一条。
前一轮（21:33:51，列那 3 条）也是模型：`tools: ['list_day_todos','list_day_todos']`，
而规则层那条路出清单时 `tools` 是 `[]`（trace 里那句是「🗑️ 删待办命中多条（列清单，不猜）」）。

**所以「1和2」这句根本没进确定性分支，直接掉给了模型。**

### 0.3 为什么没进：规则层没有"选中其中几条"这条路

`app/modules/planner.py:5737-5748`，学生一次报多个序号时：

```python
    if idxs and candidates:
        picked = []
        for idx in idxs:
            i = len(candidates) - 1 if idx == -1 else idx - 1
            if 0 <= i < len(candidates):
                picked.append(candidates[i])
        if len(picked) == 1:
            return {"status": "ok", "proposal": _todo_remove_proposal(picked[0]),
                    "todos": [picked[0]]}
        if len(picked) > 1:
            # 学生一次点了好几条：一次只删一条（不猜、不批量），列出来请他挑一条
            return {"status": "many", "todos": picked, "reason": "一次只能删一条"}
```

**`len(picked) > 1` 被降级成 `many`**，注释里那句「一次只能删一条（不猜、不批量）」是当时的决定。
`many` 到了上层只会**再列一遍清单**（`main.py:4910`），而清单里已经没有"取消/全删"的出路 ——
学生点了两条，系统反问"你要删哪一条"，这就是原地打转。

### 0.4 批量卡其实早就有，只是这两条路不给它

`app/modules/planner.py:5204`：

```python
def todo_remove_batch_proposal(items: list) -> dict:
    """把"你列的这几条**全都要删**"包成一张**批量**确认条（人话：一次列清、一次点头）。

    为什么要一张卡、不挂 N 张单条卡：学生说的就是"都"——那就该**一次点头、一次删完**。
    挂 N 张条让他点 N 次，等于没听懂他的话（学生原话："去思考学生表达的意思，
    不是字面上的"）。
    """
```

前端也有现成的渲染（`app/static/student.html:1651`：`o.kind === "todo_remove_batch"`，
一张卡、一个【确认删除全部】）。

它现在只在两个 status 上被调用（`main.py:4854` 去重 / `main.py:4886` 全都要删），
**"我挑中这几条"没有对应的 status，所以永远走不到它。**

### 0.5 前端那句话术也会跟着错位

`app/static/student.html:1680-1685`：只要拿到**两张以上** `todo_remove` 卡，就自己写一句

```js
? `🗑️ 有 ${dels.length} 条对上了你说的话，点选你要删的那一条（删除找不回来）：`
```

它把后端那句「两张确认条已经挂出来了」**盖掉**了。而学生给的压根不是"话"，是编号 1 和 2 ——
「对上了你说的话」这句在这个场景里是错的。（不用改前端：改成批量卡之后，这条路不会再被走到。）

### 0.6 附带一处：带「第」字连写多条会漏

`_pick_todo_indexes`（`planner.py:4837`）第 ① 条的字符类是
`[0-9一二三四五六七八九十两\s、,，/和跟与]` —— **没有「第」**。实测：

```
'1和2'          cap=3 -> [1, 2]   ✓
'1、2'          cap=3 -> [1, 2]   ✓
'第1和第2条'      cap=3 -> [2]      ✗ 漏了 1
'第一条和第二条'     cap=3 -> [1]      ✗ 漏了 2
'第2、3条'       cap=3 -> [2, 3]   ✓
```

学生说「第一条和第二条」时只会选中一条 —— 另一条他不点了，系统也不会提醒。

## 一、修法

### 1.1 `planner.py:5746-5748`：多条选中不再降级成 `many`（3 行）

```python
        if len(picked) > 1:
            # ★ #117：学生一次点了好几条，就是"这几条我都要删"——挂一张批量条、点一次删完。
            #   旧写法降级成 `many`（"一次只能删一条"），上层只能再列一遍清单问他哪一条，
            #   他刚说了两条、系统反问一条，就是原地打转；实测这句还会掉给模型，
            #   模型调两次 propose_todo_remove 挂出两张卡，要他点两次
            #   （用户截图：打乒乓球 + 健身房，两个【删除这条】按钮）。
            #   `todo_remove_batch_proposal` 就是为这一幕写的（见 `:5204` 的注释）。
            #   红线没破：这只是**提案**，他点【确认删除全部】之前一条都不会删。
            return {"status": "pick", "todos": picked}
```

### 1.2 `main.py`：`many` 分支**之前**加一支 `pick`

`main.py:4910` 那个 `if status in ("many", "unclear")` 的**上面**插入：

```python

            if status == "pick" and len(res.get("todos") or []) > 1:

                return {
```

> ⚠️ 位置是有讲究的：必须排在 `many` **之前**。排在后面就永远轮不到 ——
> `many` 的条件是 `status in ("many","unclear")`，`pick` 不在里面，但
> **两个分支之间还夹着 `empty` / `_blind_recent` 那几支**，插在 `many` 之后容易插进
> 别的分支的 `if` 里。**接在 `if status in ("many","unclear")` 前面一行最稳。**

### 1.3 `planner.py:4837`：字符类补一个「第」（1 行）

```python
    m = re.search(r"第\s*([0-9一二三四五六七八九十两\s、,，/和跟与第]{1,20}?)\s*(?:条|个|项)", t)
```

只加末尾那个「第」，让「第1和第2条」能整段被捕获（`findall` 随后会跳过「第」这个非数字字符）。


## 二、判断与理由

### 2.1 为什么修后端、不修前端那句文案

前端那句话之所以出现，是因为它收到的是**两张独立的卡**。把文案改成"你点的这几条"，
屏幕上仍然是两张卡、两个按钮、点两次 —— **判据错了，改话术只是把错的说得好听**。
反过来，只要后端给一张 `todo_remove_batch`，前端 `:1651` 那条路直接把整张卡画出来，
`:1680` 那句根本不会被走到。

### 2.2 「一次只能删一条（不猜、不批量）」这个旧决定该翻

那条注释的顾虑是"猜错就删错了"。但这里**不存在猜**：`picked` 是学生自己报的序号，
按屏上清单顺序取的（`_pick_todo_indexes` 只认"整句就是个序号"）。要防的不是猜错，
是**误点**——而误点在批量卡上同样有【取消】，且卡上把每条原样念出来。
所以"不批量"在这里只留下代价（点两次、还以为没生效），没有换来安全。

### 2.3 为什么不在模型那边收敛（调两次工具 → 合并成一张卡）

可以做，但方向反了：**"学生说了几条"这一步在规则层就能算死**，交给模型算等于
每轮多花 3-4 次工具调用（实测这一轮 2.6s、4 次调用）。而且模型这条路本来就该是兜底，
不该是"删两条"的主路。规则层接住之后，模型这条路自然不会再被走到。

### 2.4 前端「有 N 条对上了你说的话」不是本单的靶子

它描述的其实是**另一种真实情形**：学生说了个模糊的名字（"图书馆"），系统匹配到两条，
让他挑。那个场景这句话是对的。**本单不改它，只是让"点名几条"这种情形不再走到它。**
