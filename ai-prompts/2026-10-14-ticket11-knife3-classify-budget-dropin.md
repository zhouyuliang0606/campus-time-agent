# 11 · 刀 3：判定层瘦身 + 与规则并行（主体已是模型本身，收益看你怎么瘦）

> 给落地 AI（Qoder）的 drop-in 施工单。**只读这文件，不要改其它 prompt。**  
> 这是「三刀降延迟」的**第三刀**（刀 1 B 见 `09`、刀 2 共享 client 见 `10`）。  
> 本刀动的是**判定层本身**，**设计风险最高**——务必按 A→B→C 的顺序做，C 谨慎。

## 0. 一句话目标与实测依据（诚实版）

`intent.py:520` 的 `classify_with_llm` 用**一次完整补全**做 4 字节级分类：  
**1249 prompt → 38 completion（实测 p50 3863ms / max 4219ms，即 ~4.2s 地板）**。  
请求体（`client.py:123-127`）只有 `model/messages/temperature`，**无 max_tokens、无 stream**。

刀 1（摘润色）、刀 2（砍握手）之后，"三次往返"的主体已经是**模型本身**  
（判定 1 次 + 引擎 1~N 次）。所以刀 3 能砍的只有两块：

1. **判定层的 prefill**（prompt 太胖，1249 token 是大头）—— 但 C（缩 prompt）已跳过大风险；
2. **判定与规则之间的串行等待**—— 而"规则已接住"句 `main.py:1280` 的门本就跳过判定。

**诚实上限**：判定仍是 1 次模型调用（TTFT + 38 token 生成）。实测**语义判定 p50 3863ms / max 4219ms**——  
这条链路的**硬地板就是 ~4.2s**，不是 1.5~2.5s。刀 3 **不消灭**这次调用；  
感知延迟压到首字 1~2s 靠的是流式（已有 `07`，本刀不重复）。  
**刀 3 真实收益有限**：A 只封顶生成、B 只确认"规则已接住句本就不等判定"（那条门已对），  
都**压不下模型固有的 ~4.2s 地板**。判定层 4.2s 是当前架构下的硬地板，  
要改善只能上 `07` 流式（感知）或未来做 C（质量风险高，已跳过）。

## 2. 具体改法

### 2.1 A · max_tokens（免费安全帽，顺手做，不指望它砍延迟）

- `client.py:100` `chat(...)` 加形参 `max_tokens: int | None = None`；在 payload 组装处加：
  ```python
  if max_tokens is not None:
      payload["max_tokens"] = max_tokens
  ```
- `gateway.py:228` 的 `ModelGateway.chat` 与 `gateway.py:287` 模块级 `chat` 都加同参并透传。
- `intent.py:520` 改成 `reply = await gateway.chat(msgs, override=override, max_tokens=64)`。
- ⚠️ **诚实说明**：合法分类输出约 38 token，`max_tokens=64` 不会截断、也**不会**显著提速  
  （生成时长由 TTFT + 38 token 决定，不是上限卡出来的）。它的价值是模型万一啰嗦/跑偏时硬截断、  
  顺手省 token 费。列为"免费安全网"，别拿它当延迟杠杆。

### 2.2 B · 与规则并行 + 判定加超时（推荐先做，零质量风险）

现状 `main.py:1280`：

```python
if (_rule_hit is None or _need_review) and not is_confirmation(message):
    _sem = await classify(message, get_conversation(session_id), override=model_config)
```

规则层 `_rule_intent`（1274）本地 0ms 跑过；`_rule_hit is not None and not _need_review`  
的句子**已经跳过判定**（这条门是对的，**不许改**）。所以"规则已接住"那一类**本来就不等判定**，  
B 在这里没有可优化空间（现状已最优）。

剩下的"规则没接住"那一类**必须 `await` 判定返回才能路由**——你**不能**靠超时把它跳过，  
否则模型还没回就 `return None` → 掉回规则/fallback → **判定直接作废、准确率掉**。  
实测语义判定 p50 3863ms / max 4219ms，任何 <4.2s 的人工超时都会误杀正常响应。

- **改法（保守、零质量风险）**：**不设人工紧超时**——保留 `client.py` 的 30s 客户端超时即可；  
  若一定要兜底异常长尾，可设 **≥6s**（只拦真卡死，不拦 p50）。规则没接住句的延迟由模型决定（~4.2s 地板），B 不改它。
- **结论**：B 的真实、安全收益 = **确认"规则已接住句不空等"现状已对、钉死断言别回退**；  
  它**不能**把判定层 4.2s 压下来。判定层 4.2s 是当前架构硬地板，改善感知只能靠 `07` 流式。
- **必须保留**：`is_confirmation(message)` 分支、`_need_review` 分支仍走 classify（确认/复核信号不能丢）。

### 2.3 C · 缩判定 prompt —— **本刀不做（用户拍板跳过）**

`_intent_system()` 1249 token 是 prefill 大头，瘦身的边际收益存在，但**设计风险最高**：  
必须保住红线 19 / 样本库优先 / 顺序（样本库→语义→关键词）/ 硬信号分支单独提前，  
且**同义词判断 100% 走模型**（规则层不补 synonym 表，近义词仍须模型归并），  
JSON 九字段 schema 也不许动——任何一项漏守都会掉判定质量，且难在测试里暴露。  
A 已封顶生成、B 已消除串行等待后，判定层剩余耗时（TTFT + 38 token）已接近地板，  
C 的边际收益不抵风险。**本刀不实现 C**；若未来确需做，另开单、配全套变异测试。

## 3. 必须钉住的护栏（缺一条就是新 bug）

1. **早退门不变**：`main.py:1280` 的 `(_rule_hit is None or _need_review) and not is_confirmation`  
   保持——这是"规则已接住就跳过判定"的正确实现，别误改成"总是跑判定"。
2. **判定质量不能降**：B 不动 prompt；C 瘦身须保红线。任何改动后 intent 枚举准确率不得掉（变异测试钉）。
3. **JSON schema 不变**：router/trace 消费的九字段一律保留，C 瘦身只减说明文字、不删字段。
4. **超时降级保持**：classify 失败/超时 → 返回 None → 掉回规则/fallback（1284-1285 已对）。  
   **B 不设 <4.2s 的人工超时**（会误杀正常判定）；只保留 client 30s 超时，异常长尾可设 ≥6s。
5. **账号/用量记账**：gateway 仍按 `user="内部:语义判定"` 记账；C 瘦身会让 `prompt_tokens` 下降  
   （好事，管理端用量统计可见）。
6. **SSRF / 守卫族 / 写库漏斗**：零影响。

## 4. 老规矩验证清单（落地 AI 必须逐项过）

- **护栏先行（先写断言，再改）**：
  - 新断言 1：`_rule_hit is not None and not _need_review` 的句子**不**触发 classify（mock 计数 == 0）。
  - 新断言 2：intent 枚举**准确率 ≥ 改前**（A/B 不动 prompt、不跳判定，理论上不降；用变异集覆盖 module/intent 各值 + 近义词归并钉死）。
- **变异打回（证明断言真能抓回归）**：
  - 把 `max_tokens` 设到 8（截断合法 JSON）→ 断言"判定有效输出率"变红；
  - 或把 1280 门改成"总是 classify" → 断言 1 变红；
  - 或（若有人给 classify 加了 <4.2s 超时）把超时设回 2.5s → 断言 2（准确率）必红。
  - 红了再改回正确值，断言转绿。
- **真机复测五句（改前/改后对比 ms）**：
  - 重点「今天几号」（2 次模型，判定占其一 ~3.1s）、「食堂几点关门」（3 次模型，判定占其一）。
  - 规则已接住类（如「帮我安排游泳」本就不判）不变，作基线。
  - **B 不改判定延迟**：规则没接住类的判定耗时仍约 ~4.2s 地板，B 的验证点是"规则已接住句不触发 classify"（断言 1）与"准确率不降"（断言 2），不指望它砍判定延迟。
- **交付纪律**：细粒度 commit（① A max_tokens 透传 ② B 钉死"规则接住句不空等"断言 ③ 若未来做 C 缩 prompt 单独 commit）
  - 打快照 + 重启 8000 复测。

## 5. 明确不做（防止范围蔓延）

- **C · 缩判定 prompt：本刀不做**（见 §2.3，用户拍板跳过）。
- **不删 classify 这层**：它的语义归并 / 近义词判断是用户原始需求，规则层不补 synonym；  
  本刀只封顶生成（A）并钉死"规则接住句不空等"（B），**不靠超时跳判定**、不消灭判定调用。
- **不把"合并判定与引擎首步"塞进本刀**：那是更深的重构（把 classify 结论喂给引擎首调用），  
  风险更高、独立于本刀，若要做另开单。
- 不碰流式（`07` 已覆盖）；不碰刀 1/刀 2 已动的文件（`polish.py` / `client.py` 的共享 client 创建）——  
  本刀若用 max_tokens 只在 `client.chat` 加一个**参数**，与刀 2 的共享 client 实例**互不冲突**（参数与实例独立）。
