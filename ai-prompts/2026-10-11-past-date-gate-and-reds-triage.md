## 二、② 已做：过去的日子不许建待办

真机引子是上一轮那两条：语义层吐了 `2023-04-18`，确定性分支照收，
卡片挂出去、学生刷新**永远找不到**它；另一条更常见 —— 卡片过夜，昨天勾的时段今天点【确认加入】。

判据只写一份：`store.is_past_date(iso)`（`app/store.py`，紧挨着 `iso_weekday_of`）。
**读不出格式的返回 False** —— 空串/"昨天"这种不归它管，免得这道闸顺手把别的错误吞掉。

查它的地方（出卡四条 + 写库两个，一共六道）：

| 位置 | 行为 |
|---|---|
| `planner.parse_add_todo` | 过去的日子 → `None`（不建卡） |
| `planner.auto_todo_proposal` | 同上（不替他挑时段） |
| `planner.span_only_proposal` | **兜底日期**是过去的 → `None`（语义层吐陈年日子的正身） |
| `planner.retime_todo_proposal` | 不许把已有待办**改到**过去的日子 |
| `POST /api/todos` | 400 +「{date} 已经过去了，不能往过去的日子里排待办」 |
| `POST /api/todos/batch` | 逐条丢过去的段；全是过去的 → 400 说清几条；混合 → 只写将来那条，**不谎报** |

## 四、① 「每周N次 = 长待办」——我建议的形状，等他认

现状（本轮实测）：`unsupported_period("每周6次去图书馆")` → 否决；
「每周两次」否决；**「每周三次」放行**（走"这一周铺三条"，下周就没了 —— 学生说的明明是长期）。
三句不一致的根在 `_EVERY_UNIT_RE` 的让路前瞻只看"后面像不像星期几"，分不清星期几和次数。

按他这句「没周N次就是长代办，可以代办加一个分支」，我打算这么做，**不加新字段**：

> 「每周N次」→ 出 **N 条 `repeat=weekly` 的待办**，每条钉在一个不同的星期几上
> （星期几由系统在那几天的空档里挑，挑不满就如实说"只排得下 M 段"）。

为什么是这个形状：`repeat=weekly` + `weekday` 已经全通了
（store 展开、`todo_occurs_on`、两份前端 JS、按天完成），批量写入 `/api/todos/batch` 也已经在了 ——
**语义正好就是"长期、每周几回"**，而加一档 `repeat="weekly_n"` 要动后端展开 + 前端两份同名逻辑，
还得回答"没定星期几的每周三次算哪三天"。等于用现有能力拼出他要的东西。

要他点头的两点：(a) 这个形状行不行（N 条 weekly，而不是新加一档）；
(b) 「每周三次」从现在的"这一周铺三条"改成"每周三回长期"，是**行为变化**（原来那三条下周消失）。

## 五、③ 那 9 条红：能修，根因是同一个洞，分大小两刀

`tests/_harness.py:61 class sandbox` 的做法是**把真实 `app/data` 整个 copytree 到临时目录**，
然后只删 `SCRATCH` 那六个文件（settings/uploads/notices/workorders…）。
`student/todos.json` 和 `intent_samples.json` **不在清理名单里**，于是测试读的是真数据：

- **7 条**（`test_06`×5 + `test_23`×2）：断言数的是"库里有几条待办"，
  数到的是他的演示数据（诊断尾巴上 `('健身','2026-10-09')` 变 `('健身','2026-10-11')` 就是它）。
- **2 条**（`test_01`、`test_08`）：`intent_samples.json` 里有今天手测灌进去的四条含「图书馆」样本，
  `match_sample("图书馆几点关门")` dice 0.444 ≥ 阈值 0.42 就接单，**还不看命中样本有没有事名**。

**小刀（我建议先做这个）**：把 `intent_samples.json` 加进 SCRATCH —— 学来的样本本来就不该进测试，
内置种子在代码里、不受影响。影响面只有 5 个文件碰样本库
（`test_06/08/16/42/intent_classify`），一轮全量能验完。**这刀修掉那 2 条。**

**大刀**：给 `student/todos.json` 一份**固定种子**（空表或写死的 fixture），测试自己造数据。
能修掉那 7 条，但 `test_05` 这类**明写要读演示数据**的测试会红（`_harness.py:113` 那句注释就是它），
得逐个改判据 —— 是一笔独立的活，不是顺手改一行。做完 README 里那句「失败 0 项」才第一次是真的。

两刀都不动产品行为，只动测试基建；但都会让**一批现在绿的断言变红再改**，
所以要他点头再动（尤其大刀）。
