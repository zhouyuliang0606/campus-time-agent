# 2026-09-26 意图兜底层：把「听懂人话」和「动手执行」切开

> 本文件是「AI 创新应用挑战赛」要求的 **AI 对话历史 Prompt 快照**之一。

---

## 一、用户 Prompt（原话摘录）

> 「所以很多的字都是接不住的，你现在能接住的都是我测试给的，你有没有什么办法」

## 二、这句话为什么是关键的一句

它不是又一条报障，是把**之前所有报障的共同病根**点破了。

前几轮的做法是"你测出一句、我补一条规则"：

| 报障 | 补的东西 |
|---|---|
| 「我要加代办」没接住 | `_ADD_INTENT` 加词 |
| 「周三加个健身」没接住 | `_ADD_TALK_RE`（动词+量词） |
| 「我要去吃火锅」没接住 | `_GO_INTENT_RE`（第一人称下单） |
| 「平时」被排成周六 | `workday_mode` |
| 「卡片呢」不弹卡 | `_FIND_CARD_WORDS` |

我数了一遍现状：

- `app/modules/planner.py`：**30 多张**关键词 / 正则表；
- `app/agent/router.py` `_QUICK_MAP`：**50 多个**硬编码关键词，而且是
  `if keyword in text` 的朴素子串匹配；
- `app/main.py`：又 4 张。

**中文口语的写法是无限的，而"你说一句我补一词"永远慢一拍。**
这是在拿字符串匹配干语义理解的活，词表加多长都收敛不了。

## 三、研判：病根是两层职责没分开

系统其实一直在做三件事，只是它们被揉在一起，所以只能一起用正则实现：

1. **听懂**（这句是不是要加待办 / 要删 / 要查 / 在找卡）
2. **抽取**（要做的事叫什么、多久、哪天）
3. **执行**（查空档、排期、出卡、写库）

其中 ③ 绝对不能交给模型（这是项目从第一天就守的红线：AI 只出提案、系统才执行），
但 **① 恰恰是模型最擅长的**。过去因为 ①②③ 揉在一起，只好连 ① 也用正则——
于是就不断补词。

## 四、方案：分层，只把「听懂」那层换掉

```
┌─ 判定层（可换、可兜底、可以交给模型）──────────────┐
│  ① 规则：30 张词表，命中就走，零成本零延迟          │
│  ② 语义：问一次 LLM，只要回 JSON 意图   ← 新增     │
│  ③ 样本库：历史成功原话模糊匹配         ← 新增     │
└──────────────────────────────────────────────────┘
┌─ 执行层（系统独占，模型永远碰不到）────────────────┐
│  查空档 · 排期 · 出候选卡 · 写库                    │
└──────────────────────────────────────────────────┘
```

**② 让 LLM 干的活只有一件**：把这句话听懂，吐一串字段。

```
输入："我要平时去吃火锅，76分钟"
输出：{"intent":"add_todo","title":"吃火锅","minutes":76,"day_hint":"工作日"}
```

拿到 JSON 之后，查空档、摊候选、出卡、写库**走的还是 `planner.py` 那套老代码**。
所以「AI 只提案、系统才执行」这条架构主张一条不破——模型连"决定排几点"的权力都没有。

**成本**：只有 ① 规则接不住才往下走一层，常规说法**零 API 调用、零延迟**。

## 五、改动

### 1. `app/agent/intent.py`（新增，核心）

| 组成 | 说明 |
|---|---|
| 意图白名单 | `add_todo / remove_todo / list_todo / find_card / retime_todo / clear_timetable / chat`。模型只许从这里挑，**自造的一律不认** |
| ③ 样本库 | 字符二元组 Dice 系数做模糊匹配（阈值 0.42）；短于 4 字不配（防虚高误伤）；系统每办成一句就学一句；`chat` 不学（免得把错误意图记进去）；上限 400 条 |
| ② 语义层 | 只输出 JSON；`confidence < 0.6` 不要；`add_todo` 的 title 要过 `planner` 的判真；没 key / 调不通 / 吐的不是 JSON → 安静返回 `None`，掉回老路，绝不崩 |
| `to_canonical()` | 把语义层读出的字段翻成「加个吃火锅，76分钟，工作日」这种**解析器认得的规范话**，再喂给老的 `parse_add_todo` / `todo_mode_proposal`——不另抄一份"从 JSON 造卡片"的逻辑 |

### 2. `app/main.py`（接入，最小侵入）

不重写任何一条确定性分支，只在**入口条件**上追加 `or _sem_intent == X`：

- `_rule_intent()`：把现有 `wants_*` 预检一遍，只为判断"规则接不接得住"，
  好让语义层只在真落空时才跑。它只是**预检**，不参与判定，漏判最坏只是多问一次。
- `_sem_done()`：只在**真出卡**时才把原话学进样本库。模型自由发挥那句不算。

覆盖 `add_todo / list_todo / find_card / remove_todo / clear_timetable` 五档。

### 3. `app/agent/router.py`（路由层同一个病）

「卡片呢」那幕的病根其实在路由：`_QUICK_MAP` 里没有「卡」，整句掉给 LLM 分类，
模型顺着"卡"联想到校园卡 → 分去 `lostfound`。

在关键词表和 LLM 分类之间插一档**样本库匹配**（零成本、离线可用）。
这里刻意**不调 LLM**——路由每句话都要走一次，加一次调用太贵；
LLM 那一档留给 `/api/chat` 的意图层。

| 批 | 钉什么 |
|---|---|
| ① 样本库 | 同义改写认得出（0.60）、无关句认不出（0.00）、太短不乱配、能自增长、chat 不学 |
| ② `to_canonical` | 字段拼成规范话；没读到就原样返回，不硬凑 |
| ③ 语义层 | 白名单外不认、把握 0.3 不要、没 key 安静返回 None、非 JSON 不认、标题判真不过就留空 |

用打桩的假 LLM 客户端，不真联网、不依赖 key。

## 七-bis、真机跑出来的一个真 bug：规则被多义词骗了

上表最后一行就是它。学生说「**我现在都有啥安排**」，`_ADD_INTENT` 里有"安排"
两个字，子串匹配分不清这里的"安排"是**名词**（日程安排）还是动词（帮我安排）
→ 判成下单，卡片上会写着「**我现都有啥**」——他想查待办，系统却要给他加一条。

这正是关键词表的天生盲区：**补词补不好**（今天补"安排"，明天还有别的词），
所以没有再加规则，而是让**语义层反过来复核规则**：

- 规则判了 `add_todo`、且话里带明显查询词（有啥 / 什么 / 哪些 / 看看 / 有没有…）
  → 复核一次；
- **只有语义层跟规则结论不一致时**才否决规则，判得一样就照旧走；
- 成本：只有这类可疑句才多一次调用，正常下单句零影响。

复核实测：

| 原话 | 改之前 | 改之后 |
|---|---|---|
| 我现在都有啥安排 | 出一张加「我现都有啥」的卡 | 念出 3 条待办，不出卡 |
| 看看能不能安排个健身 | — | 语义层同意是下单 → 照旧出卡（不否决） |
| 帮我安排个健身 | 出候选卡 | 出候选卡（不含查询词，不触发复核） |

## 八、已知边界（如实写）

- ~~当前机器没配 key~~ → 用户已于 2026-09-26 配好（管理后台 / `deepseek-chat` /
  官方地址），语义层已真机验证，见上。
- ③ 样本库只能覆盖"说过的"，泛化弱于 ②，但**离线可用、零成本、越用越准**，
  同时也是 ② 的缓存（LLM 判定过的说法存进来，下次连 API 都不用调）。
- 阈值（`_SIM_THRESHOLD=0.42`、`confidence<0.6`）都是**偏保守**取的：
  这一层的设计取向是「宁可漏判掉回老路，也不可替学生办错事」。
- `app/data/intent_samples.json` 已列入 `.gitignore`：它是运行时"每办成一句学一句"
  攒下来的私人语料，不该进公开仓库；种子 7 条内置在代码里，删了能重新长起来。
