## 一、修法

### 一.0 动手前先做一次真机判别（**不许跳过**）

沙箱没配模型 Key，语义层返回 None ⇒ §0.2 那道闸在沙箱里是**通的**，测不出真机行为。
所以「电梯坏了」为什么没出卡，**在沙箱里只能确定两条可能路径，不能确定是哪条**：

| 路径 | 判别方法 | 症状 |
|---|---|---|
| **A. 触发词档被挡** | 真机问一句「电梯坏了」，看 `/classify` 返回的 `module` 是不是 `custom:c8ef8355` | 不是 ⇒ 走 A |
| **B. 归对了但模型没调工具** | 同上，`module` 是 `custom:c8ef8355`，但没弹登记卡 | 是 ⇒ 走 B |

**判别的意义**：A 改 `main.py:2307`，B 改 `custom_prompt`（`custom.py:71`）。
**两条路的修法完全不同，不要凭猜动手。**

### 一.1 若判为路径 A：放宽触发词档（但只放"不是办事"的那一半）

`main.py:2309` 现文 `if _eff_intent in (None, INTENT_CHAT):`

建议改成：**命中触发词 + 不是问句 ⇒ 接管，除非模型明确判成"办事类"**。办事类清单
（`intent.py:46-52` 那七个别让路）：`ADD_TODO / REMOVE_TODO / RETIME / DONE / CLEAR_TIMETABLE /
LIST_COURSE` 之外的一律让位给触发词。

```python
        _CUSTOM_YIELD_INTENTS = (INTENT_ADD_TODO, INTENT_REMOVE_TODO, INTENT_RETIME,
                                 INTENT_DONE, INTENT_CLEAR_TIMETABLE, INTENT_LIST_COURSE)
        if _eff_intent not in _CUSTOM_YIELD_INTENTS:
            _svc_hit = match_service_by_trigger(message)
            ...
```

**为什么这样切**：触发词是**管理员亲手登记的**，属于项目定义里的"硬信号"（红线 5）；
而模型的 `custom_record` / `chat` 是弱信号。硬信号优先，这一档的设计本意就是这个
（`:2299-2303` 的注释自己写着「触发词是硬信号…光靠判定层判对不够」）。
"办事类"六个意图让路，是因为那几种情况学生已经明确让系统去动日程了，不该被报修劫走。

⚠️ 这条改动在**判定层优先级**上，是这一单风险最高的一笔。改完必须跑全量，且必须确认
`test_54`（自建服务意图）与 `test_75`（部门分流）两项都不掉。

### 一.2 若判为路径 B：`custom_prompt` 把"该不该出卡"讲死

`custom.py:71-87` 现在只说「学生说清楚了几项就填几项，没说的就留空」——
模型面对「电梯坏了」这种一条字段都没有的话，很可能选择**先追问**而不是出卡。

补一句硬口径（放在现有「你只有一个动作」那段里）：

> 学生这句话已经命中这项服务的触发说法（**管理员登记的**），那就是**要登记**，不是要闲聊。
> 就算一个字段都没说，也**必须**调用 `propose_custom_record` 挂出空卡让学生补 ——
> 追问也一样要挂卡（卡上留空，确认页会让他填），别用聊天气泡问一句就完事。

这条只改提示词、不动代码逻辑，风险最低。

### 一.3 出卡台词与栏目都按 `_wo_kind` 走（第 1 条，与 A/B 无关，必修）

`main.py:2470-2477`：

- `"module": "express"` → 设施报修**不该归快递栏**。建议 `_wo_kind == "设施报修"` 时给 `"planner"`
  （或另起一个栏目键，取决于前端认哪些值 —— **动手前先核 `REGISTRY` 与前端导航的合法值**，
  不许自造一个前端不认识的 module）。
- `answer` 改成按 `_wo_kind` 分两句：

  - 设施报修：「🔧 听起来是**设施坏了**。要不要上报？下面这条确认条点【确认上报】就会生成工单（也可填补充描述）；点【取消】就不上报，数据一点都不会动。」
  - 其余四种：保留现在这句快递/外卖原文。

**为什么必须一起改**：§二.2 会讲 —— 只修"能不能出卡"，会把「不出卡」的尴尬换成「出卡但念错字」的尴尬，
**后者更糟**。

### 一.4 两处判定补词（第 3 条）

**(a) `_FACILITY_RE`（`planner.py:1806`）补「网络」**，但要防误伤：
「网络」太泛（网络课？网络中心在哪？）。建议写成 **`网络\s*(坏|断|不通|连不上|没网)`** 这种
"网络 + 故障状态"的组合，而不是孤零零一个「网络」。同理可考虑补 `宽带`。

**(b) `looks_like_question` 的疑问词表补「多久 / 多长时间 / 几天 / 啥时候能」**（§0.5 上半）。
⚠️ 这条要**格外小心**：`looks_like_question` 是全项目共用的闸（`main.py:2307` 也用它），
补词会同时影响好几条路。补完必须跑全量，看是否有本该出卡的句子被判成问句。

**(c) 顺带记一笔**：`5e702308` 把「报修要多久」登记成了触发词（运行时数据，不在 git）。
这是管理员输入的问题，不是代码 bug；**不要改代码去迁就它**，最多在管理端校验里加一句提示。
本单不动它。

### 一.5 docstring 改口

`planner.py:1829-1832` 的返回类型补上「设施报修」（第五种），与 `_work_order_kind` 实际行为对齐。

## 二、判断与理由

### 2.1 为什么不能按报告说的"放宽 `_WORK_ORDER_RE`"

因为那两条是**两套不同的台账**，走错一套演示就露馅：

| | 通用工单链 | 自建服务链 |
|---|---|---|
| 进门 | `_WORK_ORDER_RE`（`planner.py:1797`） | `match_service_by_trigger`（`store.py:1955`） |
| 出卡 | 「上报驿站：<type>」（`main.py:2452`） | 「登记「电梯报修」：…」（`custom.py:44`） |
| 落库 | `workorders.json`，**驿站**处理 | `custom/<id>.json`，**按 `dept` 归后勤** |
| 界面 | 快递/外卖栏 | 「我的上报」 |

分镜 `:182` 要的是右列（**归后勤**）。放宽 `_WORK_ORDER_RE` 会把它推到左列（**上报驿站**）——
**卡会出来，但归错部门**，而 `:187` 紧接着就要演"驿站端看不到这条"，
错部门之后这一镜的逻辑就整个塌了。

`store.py:1958-1962` 的注释自己就写着这件事：

> 内置那项「快递/外卖问题处理」(table=workorders) **不参与**这句到卡片的自动路由…
> 两套台账不是一回事。真机上「快递丢了」必须照旧出工单上报卡，这条由 `test_54` 钉着。

**所以：与其放宽左列的门，不如让右列的门真正生效。** 而右列的门（`match_service_by_trigger`）
实测是好的，只是被 §0.2 那道闸挡着，或者被模型的"先追问"习惯吃掉。

### 2.2 为什么一.1 和 一.3 必须同一笔改完

现在「电梯坏了」很可能**两处都不通**（既没归到自建服务，也不命中通用工单）。
如果只修一.1/A：

- 归到 `custom:c8ef8355` 成功 → 走自建服务链 → 不经过 `main.py:2471` → **那句话不会念错**（还好）
- 但如果哪天 A 没生效、掉到 `main.py:2445`（比如学生说的是「宿舍网络坏了要报修」，这句
  `_WORK_ORDER_RE` **是命中的**，§0.2 实测过）→ `_wo_kind = 设施报修` → **屏幕念「你的快递/外卖可能出了问题」** → 当场露馅

「宿舍网络坏了要报修」正是分镜 `:188` 的演示句。所以 **一.3 是独立的风险点，A 通了也不能省。**

### 2.3 修之前必须先做 §一.0 的判别

这是本单唯一"不给结论"的地方，理由写在 §一.0：沙箱没有 Key，语义层返回 None，
**闸在沙箱里天然是通的**，所以沙箱测出来的"能出卡"是假绿（#14 那笔"测试全绿、真机照样错"同款）。
真机一句 `/classify` 就能定，别猜。
