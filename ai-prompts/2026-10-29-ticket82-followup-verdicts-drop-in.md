## 一 要做的三条

### 1.1 「改改」：加，但它救不了那句

**实测**（我跑的，不是推测）：

```
_pick_todo_name('改改时间')                    -> '改改时间'        ← 残渣
_pick_todo_name('你帮我想一个周末的时间改改过去') -> '你帮我想一个时间改改过去'  ← 残渣
_pick_todo_name('游泳时间撞了，改一下时间')       -> '游泳时间撞了改时间'      ← 也是残渣
```

**第三行是关键**：连截图第一轮那句（真机上**成功了**、念出了「游泳」）在函数级抠出来的也是残渣。

那真机为什么成？因为 `sem.get("title")` 给了「游泳」（语义层从上下文读出来的），
`build_retime_existing_proposal` 优先用它；`_pick_todo_name` 那条路根本没参与。

⇒ **两件事要分开说清楚**：

| | 靠谁 | 加「改改」有帮助吗 |
|---|---|---|
| **判定**（这句是不是改期） | 现在**全靠语义层**（`wants_retime_todo` 认不出） | **有** —— 规则层稳定接管，不看模型脸色 |
| **事名**（改哪一条） | 语义层给 title；抠不出来就是残渣 | **没有** —— 加了也还是残渣 |

**所以裁决是：加，一行字符串，`_RETIME_WORDS` 里补一个「改改」。**

但**必须在单里写死这句话**：加了之后，「你帮我想一个周末的时间改改过去」仍然会走到
`empty`（没找到那条待办）—— **除非语义层给了事名**。它不是修好，是**让失败方式变稳、变诚实**。

真正的病根是 `_pick_todo_name` 在改期句上普遍抠残渣（三行实测都在），那是**事名残渣族**，
`#77` 单据 §四.2 明令禁改那张表，**另立一单**，不在本刀内。

**验法（必须有正控）**：
- 负控：`wants_retime_todo("改改时间") == True`
- 正控：`wants_retime_todo("改改错别字")` 也 True —— **这没关系**，planner 语境里没这个说法；
  但它证明"我们没打算用词表区分语义"，别在测试里写成"不误伤"

### 1.2 待办本来就在周六 → 换修法：**把旧日期排到最后**，不是删掉

学生那条待办在周六，他再说「改到周末」，意图大概率是**换到周日**（他已经在周末了）。
但如果周日满、下周末也满，**回周六内部换个时段**仍然是个可行的答案 —— 比"周末都排满了"强。

所以不是 `cand = [d for d in cand if d != old_date]`（删掉），而是：

```python
# 旧日期排到最后：学生会说「改到周末」而他本来就在周末，多半是想换到另一天；
# 但另一天排不下时，回到"这一天里换个时段"仍比"排满了"更有用。
old_d = old.get("date", "")
if old_d in cand:
    cand = [d for d in cand if d != old_d] + [old_d]
```

**这一行放在 `next(...)` 之前**，其余不动。

**这条的本质是一句可以复用到别处的话**：改期时"目标日期集合"里，
**那一天本身不是不能选，是不该优先选**。

### 1.3 `unclear` 的话术要和来源对上（三条里最该做）

现状：`unclear` 有两个来源，共用一句「新时间我没听清」——

| 来源 | 学生实际处境 | 现在说的话 | 错在哪 |
|---|---|---|---|
| 没给新时间 | 他什么都没说 | 「新时间我没听清」 | 勉强能过 |
| 给了新日子但那天排不下 | 他说得**很清楚**，是那天满了 | 「新时间我没听清」 | **当众说错话** |

而且 `#82` 已经为"周末全满"单造了 `weekend_full` 一个标记 —— **别再长出第二套**。

**统一成 `reason` 字段，三种来源一个机制**：

```python
{"status": "unclear", "reason": "no_time", "todos": [old]}   # 没给新时间（#81 的空改动 / 压根没说）
{"status": "unclear", "reason": "no_slot", "todos": [old]}   # 给了新日子，那天（或那几个候选日）排不下
```

把现有的 `weekend_full` **并入 `no_slot`**（它就是 no_slot 的一个特例，没有独立的语义）。
`main.py` 那一支按 `reason` 选话术：

- `no_time` → 「🔕「{title}」现在是 {old_label}。想改到哪天、或者几点？」（**就是现在这句，不动**，#81 已验过）
- `no_slot` → 「🕘 那天排不下了（你那会儿有课/已经有安排）。换个日子？比如往前挪一天。」

**两个技术要求**：
1. `reason` **两个来源都要标**，不许只给新来源标、老来源留空 —— 那是同一个判据两个写法（红线 4/11）。
2. `main.py` 那支**按 reason 分支前必须先取默认值**：老调用方/老测试可能拿到没有 `reason` 的 `unclear`，
   `resp.get("reason") or "no_time"` 兜一下，别 `KeyError`。

## 二 不做的三条

### 2.1 「改到下午」仍算空改动 —— 不做

看着和「改到周末」同构，**但有一条本质区别**：

| 句子 | 追问后学生再说一遍 | 结果 |
|---|---|---|
| 改到**周末** | 「周末」 | **同一句追问，死循环** ← 这才是 #82 要治的病 |
| 改到**下午** | 「下午三点」 | 能办 ✓ |

「下午」覆盖 12:00~18:00，**14:00 和 17:00 差别很大**，追问"具体几点"是负责任的问法；
而「周末」只有两天，学生已经说到最小粒度了，再问就是没在听。

**判据：会不会死循环。不会，就不做。**

（真要做，得让 `pick_free_slot` 认时段偏好并保持原时长——那是另一笔，不是加个词表能了的事。）

### 2.2 `test_75:535` 的短路写法 —— 不改

`tests/test_75_dept_routing.py:535`：

```python
code = code or fn().summary(name)     # 第一批发失败 ⇒ 后面 9 批压根不执行
```

**`grep -rln "code = code or" tests/*.py | wc -l` = 19。** 十九个测试文件都是这个写法，是框架级的。

- 它**不影响正确性**（失败还是失败，只是看不到全貌）
- 改它要动十九个文件的 `main()`，封版前做这件事是纯风险
- 遇到它挡住排查时，**直接单批跑**：`python -c "import sys;sys.path.insert(0,'tests');import test_75_dept_routing as m; m.batch_x()"` —— 绕过，不改

### 2.3 `note`/`category` 在任何改期里都会丢 —— 不做，但改一句演示口径

提案从来不带这两个键，确认口 `main.py:6469-6470` 是 `body.get("note") or ""` ⇒
**任何一次改期都会把备注和分类抹成空串**（不只是空改动，#81 只堵了"白丢一次"）。

修它要动写库路径（改成"没给就沿用旧的"），**风险级别和 #82 完全不同**，封版前不碰。

**但这条有一个交付侧的动作，必须做**：
`docs/演示视频分镜.md` 的「§四 别演清单」加一行 ——

| 想演的那句 / 那个动作 | 实测结果 | 改成 |
|---|---|---|
| 拿改期演「备注/分类还在」 | 提案不带 `note`/`category`，确认后两项被抹成空串 | 别演；要演改期就只说时间 |

**这条是本次六条里唯一影响交付物的**，别漏。
