# 65｜「今天有什么课」被答成待办：模糊匹配 + 宽判据 + 自学习固化（drop-in）

> 现象（用户真机 + 沙箱双重复现）：问「我今天有什么课」，
> **普通模式答「📋 你目前的待办（共 2 条）· 做题 / 约会」**，Agent 模式调 `get_day_courses` 答对 3 门课。
>
> 这不是"模型能力不够"，是**三段判据叠在一起，把一句问课的话送进了列待办分支，
> 然后把这次错判当成"办成功了"记进样本库**——下次更准地错。

---

## 〇 现场事实（2026-10-26，HEAD = b36c8ad，8022 沙箱 + admin1 的真实 14 门课表）

### 复现（普通模式 vs Agent 模式，同一句、同一份课表）

```
--- 普通模式 ---  module: planner
📋 你目前的待办（共 2 条）：
· 做题｜2026-10-27（周二）14:00-16:00
· 约会｜2026-10-30（周五）15:40-18:40
trace: 🧠 听成「看待办列表」｜依据：样本库 → 🧭 判定 → 📋 列出待办（系统读取）

--- Agent 开 ---  module: planner
今天（周一）你有 3 门课：
- 08:00~09:40 高等数学（教三301）
- 10:05~11:45 大学英语（外语楼204）
- 14:00~15:40 数据结构（机房B）
trace: … → 🔧 get_day_courses({"day":"周一"}) → 📦 工具结果 → 💡 最终回答
```

Agent 模式对，是因为 #61-C 的短路点在 `3b` 之前，**根本走不到列待办那条分支**。
普通模式错，是因为它走到了。所以这条 bug 与模型无关，**是判据链的问题**。

### 根因链（三段，逐段有据）

**第一段：模糊匹配的阈值把"问课"吸进了"问待办"。**

`app/agent/intent.py:383 match_sample()` 用 Dice 系数在样本库里找最像的一句，
阈值 `_SIM_THRESHOLD = 0.42`（`:261`）。实测这一句对库里各样本的分数：

```
1.000  list_todo   '我今天有什么课'      ← 测试跑一次就自动学进去的（见第三段）
0.667  list_todo   '今天有什么代办'      ← 原本就在库里，0.667 > 0.42，照样命中
0.364  list_todo   '我有什么代办'        ← 不到阈值，不命中
```

⇒ **就算把学进去的那条删掉，`今天有什么代办` 这条也会以 0.667 命中。**
所以"删样本"不能止血。这一条是实测出来的，别在动手前先去做无用功。

`_SIM_THRESHOLD = 0.42` 本身不能随便调高：注释（`:404-409`）记着"我想去健身"vs"我想去游泳"= 0.73
正是靠这个阈值命中的，调高会打断那一路。**要修的是下面第二段的方向性，不是这个全局数字。**

**第二段：`3d` 列待办分支无条件相信语义层。**

`app/main.py:3371`

```python
if (wants_list_todo(message) and not _rule_veto) or _sem_intent == INTENT_LIST_TODO:
```

`wants_list_todo()`（`planner.py:3262`）本身是干净的——它只认"待办/代办/待办列表"这些词，
「我今天有什么课」**不会命中**它。真正放行的是后半句 `or _sem_intent == INTENT_LIST_TODO`：
只要语义层（或样本库）说是 list_todo，这条分支就接，**不再看句子里有没有在问课**。

对比：**"加课优先于加待办"这条已经做了**——
`main.py:3734` 那句 `and not wants_add_course(message)`，注释写着「末尾的 `and not wants_add_course(message)`
是「加课优先于加待办」的硬闸门」。
⇒ **"查课优先于查待办"这一半从来没做**。同一个业务上的对称原则，只做了一半。

**第三段：`_sem_done()` 把"返回了"当成"办成了"，于是错误被固化。**

`app/main.py:3271`

```python
def _sem_done(resp: dict | None) -> dict | None:
    """语义层命中、并且真的出了卡 → 把这句原话学进样本库（越用越懂）。

    只在**办成了**的时候记。模型自由发挥那一句不算——那会把错误意图学进去。
    """
    if resp is not None and _sem_intent:      # ← 判据是"返回了"，不是"出了卡"
        remember(message, _sem_intent, _sem or {})
    return resp
```

docstring 写的是「**并且真的出了卡**」，实现判的是 `resp is not None`。
而**列待办分支也返回响应**（念了一遍清单，`options` 为空），于是：

```
问课 → 判成 list_todo → 列待办分支返回 → _sem_done 认为"办成了"
     → remember("我今天有什么课", "list_todo")
     → 样本库多一条精确样本，下次 Dice = 1.000，永久命中
```

**这是一个自我强化的闭环，实测抓到了闭环本身**：删干净 → 跑一次 → 库里又冒出
`{'text': '我今天有什么课', 'intent': 'list_todo', 'hits': 1}`。

而 `:3293` 有一段注释早就写下了这个教训：
「⚠️ 也**不走 `_sem_done`**：`_sem_done` 里面是 `remember()` 学样本那一步 ——
**把一句问话学成模板，下次近似说法照着错**。」
⇒ 同一个坑在 `_asking_what_to_do` 那档被刻意绕开了，**列待办那档没绕**。

### 真实库里的脏样本（`app/data/intent_samples.json`，68 条）

```
hits=3  '今天有什么课'   → list_todo
hits=1  '今天有课吗'     → list_todo
```

`hits` 在增长，说明每一次都命中并强化。全部 14 条 `list_todo` 样本里只有这 2 条是错的，
其余都含"待办/代办/安排/该干啥"，判得对——**别顺手把它们一起删**。

### 为什么只有普通模式出问题

```
3a-c 确认落空兜底  ……………………………  ← 都在短路点之上，Agent 模式照跑
2971  if _agent_mode: return 引擎   ………  ← Agent 模式从这儿走
3371  3d 列待办  ………………………………  ← 普通模式走到这儿，被 or 放行
```

顺带一个观察：用户是从**管理端用量台账**发现"Agent 模式调了一次工具"的。
那条记录就是"这一句花了 1 次模型调用"的证据，也是本单验收时可以用的凭据。

## A 修 `_sem_done` 的判据：让实现追上 docstring（本单最重要的一改）

`app/main.py:3271`

```python
        def _sem_done(resp: dict | None, readonly: bool = False) -> dict | None:
            """语义层命中、**并且真的办成了** → 把这句原话学进样本库（越用越懂）。

            ⚠️ 判据必须是"这次真的办成了"，**不是"这条分支返回了"**（#65）。
               列待办、查课、找卡落空这些分支也返回响应，但它们什么都没办成
               —— 把"念了一遍清单"当成"办成功了"，就会把错判固化成模板：
               下一次近似说法直接命中，越用越准地错。
               `:3293` 那句注释记的就是这个坑，当时只在 `_asking_what_to_do` 一档绕开了。

            为什么用显式参数 `readonly=True`、不去猜 `resp` 的形状：
              现场 7 个调用点里，`main.py:3432`（改期）传进来的**就是提案对象本身**
              （有 title/date/start，没有 `options` 字段），它是一等一的"真办成了"。
              若按"有没有 options"判，会把它一起误停 —— 那是拿一个隐式形状约定
              去赌另一处的调用方式，正是本项目最贵的那类 bug。
              所以：**该不该学，由调用方用一句话声明**，函数不猜。
            """
            # 自证：声明成"只读"却挂着卡，说明调用方判错了，当场说出来（别静默）
            if readonly and isinstance(resp, dict) and (
                    resp.get("options") or resp.get("awaiting_choice")):
                print("[WARN] _sem_done(readonly=True) 却带着 options/awaiting_choice"
                      f"：{str(resp.get('answer'))[:40]}")
            if resp is not None and _sem_intent and not readonly:
                try:
                    remember(message, _sem_intent, _sem or {})
                except Exception:
                    pass
            return resp
```

## B 补"查课优先于查待办"这一半（与已有的"加课优先"对称）

### B1. `app/modules/schedule.py` 新增一个判据（紧挨 `get_day_courses` 之前）

```python
# 「他在问课，不是在问待办」—— 与 planner 的 `wants_add_course`（加课优先于加待办）对称。
# 为什么必须有：语义层/样本库的模糊匹配会把「今天有什么课」判成 list_todo
# （实测 Dice 0.667 撞上样本「今天有什么代办」，阈值 0.42），
# 于是 `main.py` 的列待办分支把它接走、用待办数据回答了关于课的问题（#65 真机事故）。
_COURSE_WORDS = ("课表", "课程", "上课", "有课", "节课", "几节课", "哪节课", "什么课", "没课", "排课")


def looks_like_course_ask(text: str) -> bool:
    """这句话是不是在**问课**（人话：问"我今天有什么课/明天有课吗"）。

    只认"课程词 + 疑问形状"，不认单纯出现"课"字：
      · 「今天有什么课」「明天有课吗」「后天几节课」→ 是
      · 「明天不上课了，我要回家」→ **不是**（那是加待办，课只是前提）
      · 「帮我把课表清空」→ **不是**（那是清空课表，另有分支）
    判错的代价不对称：多说"是"会把加待办抢走，少说"是"会答成待办清单。
    所以宁可窄——只要句子里还带着明显的"办事动作"，就交回给别的分支。
    """
    t = (text or "").strip()
    if not t or len(t) > 40:
        return False
    if not any(w in t for w in _COURSE_WORDS):
        return False
    # 带明确"办事"动作的不算问课（与 wants_add_todo / 清空 / 删除同一批词，宁窄勿宽）
    if any(w in t for w in ("删", "清空", "取消", "加一节", "加节", "改成", "换到", "挪到")):
        return False
    return any(w in t for w in ("什么", "哪些", "几", "吗", "?", "？", "有没有", "有没有课"))
```

> 这几个词表**不要**从别处 import 拼装（那是"同一件事两个写法"）。
> 如果实现时发现 `planner` 已有可复用的课程词表，就**引用它**，不要复制一份。
