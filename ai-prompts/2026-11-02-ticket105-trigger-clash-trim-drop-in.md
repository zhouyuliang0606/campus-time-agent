# 105 · 你输「教室报修」，它跟你吵「空调不制冷」—— 模型编的一条多余触发词，把整份定义毙了

> 施工单。改 `store.py` 的三处 + `main.py` 的两处。
> 起因：用户 2026-11-01 23:47 在后勤报修页输「教室报修」，点【建成一项后勤服务】，收到 400。
> 报错念的词跟他输的那句话**一个字都不重合**。

## 〇 现场事实（全部实测，可复跑）

### 0.1 用户看到的一幕

输入框：「教室报修」→ 点【建成一项后勤服务】→

> ❌ 没建成：HTTP 400: 生成的定义不合规矩：触发词「空调不制冷」和已有服务「宿舍报修」的「空调不制冷」撞了
> （两个互为子串，命中哪一边要看长度，等于把同一句话交给两个窗口）。
> 改个更长的说法，比如「空调不制冷登记」「空调不制冷怎么查」。

**用户输入的是「教室报修」。**「空调不制冷」这五个字他从头到尾没打过。
第一反应必然是「系统坏了」。

### 0.2 那五个字是模型自己编的 —— 真跑一次就复现

`main.py:5353` 的 `_SERVICE_PROMPT`，`idea = "教室报修"`，真调一次模型，原话（未删改）：

```json
{"name":"教室报修","triggers":["教室灯坏了","投影仪打不开","空调不制冷","桌椅损坏要修","多媒体设备故障"],
 "collect_fields":["教室编号","故障设备","故障描述","报修人联系方式"],
 "reply_template":"已登记报修，维修人员会尽快处理，请留意驿站通知。","table":"repair"}
```

5 条触发词，**第 3 条就是「空调不制冷」**。它撞的是「宿舍报修」的那条（用户第二张截图，
`app/data/services.json` 实测一致）：

```
宿舍报修 / 后勤 / repair
  triggers: 宿舍灯坏了 / 水管漏水怎么报修 / 空调不制冷 / 门锁坏了找谁 / 报修要多久
```

### 0.3 最要命的一条：报错给的两个「改法」，自己都过不了

判据是**双向子串**（`store.py:1875`，`t in oth or oth in t`）。实测拿它自己建议的说法去跑：

| 报错建议的说法 | 实测结果 |
|---|---|
| 空调不制冷登记 | **撞**（「空调不制冷」是它的子串） |
| 空调不制冷怎么查 | **撞**（同上） |
| 教室空调不凉 | 通过 |
| 教室空调坏了 | 通过 |

它说「**改个更长的说法**」——但**加长必然让新说法包含旧说法**，正好踩中 `oth in t` 这一半。
这个建议的方向是反的：照它改，永远过不去。

### 0.4 一份好定义，被一条多余短语毙掉

0.2 那份定义里，**5 条触发词有 4 条是干净的**：

```
教室灯坏了      保留
投影仪打不开     保留
空调不制冷       ← 撞「宿舍报修」→ 剔掉
桌椅损坏要修     保留
多媒体设备故障    保留
```

剔完剩 4 条，**互不重复、也都不撞任何已有服务**（实测逐条跑过）。
这服务建起来完全能用，只是少一句「空调不制冷」——而那句本来就不该归它管
（宿舍的空调和教室的空调是两个地方，`match_service_by_trigger` 也没法靠这一句分）。
**现在的代码因为这一条，把另外 4 条一起退了。**

### 0.5 根子在 prompt：模型根本不知道有哪些服务

`_SERVICE_PROMPT`（`main.py:5353-5363`）全文里**没有一个字**提到已有服务。
模型是闭着眼睛生成的 —— 它写「空调不制冷」不是犯错，是它压根不知道这个词被占了。
**判据要求模型避开一个它看不见的东西，那是判据的问题，不是模型的问题。**

### 0.6 但「撞了就拒」不是 bug，是 #54 定的

`tests/test_75_dept_routing.py:506-515` 的 E8/E9 两条，明确钉了「互为子串 → 拒」：

* E8：`triggers=["我丢了饭卡了啊", "捡到东西交别处"]` —— 第 1 条把已有的「我丢了饭卡」包住了
* E9：`triggers=["我快递丢了", ...]` —— 撞内置那项的「快递丢了」

这两条**必须保持绿**。它们防的是「同一句话交给两个窗口」，
而 0.2 那件事防的是「多写了一句废话」。**这两件事在现在的代码里长得一模一样** ——
这单要做的就是把它们分开。

## 一、修法

### §1.1 撞的那条剔掉，剔完还有 ≥2 条就放行

`store.py:1759` 附近加一个常量（**别复用 `TRIGGER_MIN_LEN`**，那是「一个字至少几个字」，
跟「留几条」不是一回事）：

```python
TRIGGER_MIN_LEN = 4            # 一条触发词至少几个字（#54 §六.2，理由在 validate_service_def）
# #105：剔掉撞车的那几条之后，**至少还剩几条**才允许这项服务建起来。
#   为什么是 2 不是 1：只剩一条触发词的服务，学生换一种说法就唤不出来 ——
#   那不是「建成了一个入口」，是「建成了只能靠背台词进入的门」。
#   为什么不是 4（照 prompt 里的 3~6 条）：模型写 4 条撞 3 条的情形现实里不存在，
#   把门槛抬高只会让本来能用的服务被退回去。
TRIGGER_MIN_KEEP = 2
```

改 `validate_service_def` 的撞车那一段（`store.py:1864-1878`），把「撞了 return」换成
「撞了剔、剔完再判」：

```python
    existing = list_services()
    short = [t for t in clean["triggers"] if len(t) < TRIGGER_MIN_LEN]
    if short:
        return None, (f"触发词「{short[0]}」太短了（不到 {TRIGGER_MIN_LEN} 个字）："
                      f"短词会吸走一大批不相干的句子。说得更具体一点，比如「{short[0]}丢了」这种带得上事的说法。")
    # ★ #105：撞车**逐条剔**，不再一条撂倒整份定义。
    #   实测：「教室报修」模型给了 5 条触发词，只有「空调不制冷」跟「宿舍报修」重了，
    #   另外 4 条干干净净 —— 退回去等于因为一句废话把整项服务废掉。
    #   ⚠️ 但剔完还要数一遍：只剩 1 条（或 0 条）时**仍然拒**，
    #      否则 E8/E9 那两条既有判据就松了（「把同一句话交给两个窗口」照样得拦）。
    kept, dropped = [], []
    for t in clean["triggers"]:
        hit = None
        for other in existing:
            for oth in [str(x) for x in (other.get("triggers") or [])]:
                if t and oth and (t in oth or oth in t):
                    hit = (str(other.get("name") or ""), oth)
                    break
            if hit:
                break
        if hit:
            dropped.append((t, hit[0], hit[1]))
        else:
            kept.append(t)
    if dropped and len(kept) < TRIGGER_MIN_KEEP:
        if dropped:
            t, oname, oth = dropped[0]
            return None, (f"触发词「{t}」和已有服务「{oname}」的「{oth}」撞了，"
                          f"剔掉它之后只剩 {len(kept)} 条，学生换种说法就找不到这项服务了。"
                          f"换个**不含**「{oth}」的说法，比如把「{t}」写成「{_suggest_alt(oth)}」。")
        return None, "这份定义一条触发词都没剩下，说说学生一般会怎么开这个口。"
    clean["triggers"] = kept
```

⚠️ **上面那个门槛必须挂在 `dropped` 为真的分支里**，写成裸的
`if len(kept) < TRIGGER_MIN_KEEP` 会误伤一类合法定义：
`SERVICE_FIELDS["triggers"] = (1, 10)`（`store.py:1753`）允许只写 **1 条**触发词，
而没撞过任何东西的 1 条是完全合规的老路 —— 裸判会把它们全拒掉。
判据是「**剔过东西之后**还剩几条」，不是「一共几条」：

| 情形 | dropped | kept | 结论 |
|---|---|---|---|
| 只写 1 条、不撞（老路，合法） | 空 | 1 | **过**（不许动它） |
| 写 5 条、剔 1 条剩 4 条（本例） | 1 | 4 | **过** |
| 写 2 条、剔 1 条剩 1 条（E8/E9） | 1 | 1 | **拒** |
| 写 2 条、两条都撞 | 2 | 0 | **拒** |

> `_suggest_alt()` 见 §1.3，就是个「换个方向」的提示小函数，不许让它去猜具体说法。
>
> `dropped` 只用于**拒的时候**说明原因。成功时**不要**把它回给界面 —— 理由见 §2.3。

### §1.2 prompt 带上已有的说法（治根，别让模型闭着眼睛写）

改 `main.py` 的 `_SERVICE_PROMPT` 生成处：把 system 消息拼成「模板 + 已有触发词清单」。

```python
def _existing_trigger_block(table: str = "") -> str:
    """把已有服务的说法列给模型看 —— 不列的话它必然撞，因为它不知道什么被占了。"""
    rows = list_services()
    lines = []
    for s in rows:
        trigs = [str(x) for x in (s.get("triggers") or [])]
        if not trigs:
            continue
        # 同类的排前面：报修撞报修的概率远高于报修撞失物招领。
        # 截断规则：每项最多 5 条、总共最多 12 项 —— prompt 是有代价的，
        # 服务建到第 30 个时不能把整张表塞进去（那时该做的是服务名检索，不是扩 prompt）。
        lines.append(f"  {s.get('name')}：{' / '.join(trigs[:5])}")
    if not lines:
        return ""
    return ("\n\n【已有的服务，它们的说法已经占用了 —— 你写的 triggers **不许**跟它们重复，"
            "也不许写成包含它们的更长句子（比如已有「空调不制冷」，就不能写「空调不制冷登记」）】\n"
            + "\n".join(lines[:12]))
```

调用处（`main.py:5399`）：

```python
        reply = await gateway.chat(
            [{"role": "system", "content": _SERVICE_PROMPT + _existing_trigger_block()},
             {"role": "user", "content": f"管理员的话：{idea}"}],
            max_tokens=400,
        )
```

### §1.3 拒的话术不许再给反向建议

新增一个小函数（放 `store.py`，紧挨着 `validate_service_def`）：

```python
def _suggest_alt(oth: str) -> str:
    """给「换个方向」的提示，**不猜具体说法**。

    为什么不能像现在这样教人「加长」：判据是双向子串，加长必然把旧说法包进来，
    正好踩中 `oth in t` 那一半 —— 实测「空调不制冷登记」「空调不制冷怎么查」两个都还撞。
    所以这里只说"换掉那个被占的词眼"，具体怎么说留给管理员。
    """
    return f"跟「{oth}」不同的地方 + 那件事怎么样了"
```

话术前后对照：

| | 现在 | 改后 |
|---|---|---|
| 拒的时候 | 「改个更长的说法，比如「空调不制冷登记」」← **照着改永远过不了** | 「换个**不含**「空调不制冷」的说法」 |
| 剔了但放行 | 无此情形（全拒了） | 静默，界面照常回「已建成」 |

### §1.4 一次性把「已剔」这件事只记日志，不回界面

`_draft_service` 里 `clean` 拿到后，剔掉的清单打一行 `print`：

```python

        print(f"[低代码] 剔掉 {len(dropped)} 条撞车触发词：{dropped}")
```

界面**一个字都不加**。理由见 §2.3。

## 二、判断与理由

### 2.1 为什么是「剔一条」而不是「整份拒」

因为**这两件事的代价差得太远**：

* 整份拒的代价 = 管理员白打一句话，还得自己想明白为什么跟「空调不制冷」有关（0.1 那一幕）
* 剔一条的代价 = 这服务少认一句本来就不该归它的说法（宿舍空调 vs 教室空调，本来就分不清）

4 条能用的触发词 vs 0 条，这不是一个需要犹豫的取舍。

### 2.2 为什么保留 `TRIGGER_MIN_KEEP = 2` 这道闸

因为「剔」不能变成「一路放过」。如果撞到只剩 1 条，那项服务等于**只有一个口令能进**，
学生换个说法就找不到 —— 那比没建更糟：管理员以为建好了，学生一次都用不上。
E8/E9 那两条既有测试正好落在这个区间（剔完各剩 1 条），所以它们**不用改口**。

**这道闸也让这单的风险收敛了**：不是「放宽校验」，是「把校验从一刀切改成有刻度」。

### 2.3 为什么不把「剔掉了空调不制冷」告诉管理员

因为**那五个字是模型编的，不是他说的**。

他现在收到的报错正是「念一个我没说过的东西」，用户已经懵了一次。
成功之后再补一句「顺便说一下，空调不制冷没加进来」—— 同一个困惑再来一次，
只是这次没有红色 ❌ 提醒他「哪里出错了」，他会以为漏了什么。

要让他知道的是「这服务建成了、5 句话里有 4 句能唤出它」，不是「模型写了 5 句我退了 1 句」。
后者是**实现细节**，属于日志。

### 2.4 为什么 §1.2 才是根，§1.1 只是止损

`§1.1` 让这件事**不再挡住用户**；`§1.2` 让它**少发生**。
只做 §1.1：模型每次都写「空调不制冷」，每次都静默剔掉——账面上没问题，
但那项服务少一条触发词这件事，将永远没人知道。

只做 §1.2：模型看到清单了，大概率不撞；但只要撞一次，又是 0.1 那一幕。
**两条一起做，才既有兑现也有收敛。**

### 2.5 为什么不在 `_SERVICE_PROMPT` 里教它「不要写跟别的服务重复的说法」

因为 0.2 的模型输出里，那 5 条**单看每一条都是合理的教室报修说法**。
它没有「重复」的自觉，是因为它手上没有那份清单。**给清单比给禁令有用** ——
禁令要求它推理「什么算重复」，清单让它直接比对。

## 附：这一单为什么值得单独提

它和 #102/#103/#104 是同一族病，但表现不同：

* #102 是**连接层**把「慢」说成「连不上」
* #103 是**判定层**把「问能力」答成「问该做什么」
* #104 是**词表层**认不出「移动」
* #105 是**校验层**把「模型的废话」当成「用户的诉求」来拒

前三条都是「少了点什么」，这一条是**多了点什么** —— 而且多出来的那句，
被当成用户自己的话念回去了。
