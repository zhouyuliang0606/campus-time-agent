## 〇 前提实测（先跑真代码，再动手）

### 0.1 单据 §2.2 那个修法**第二天就不成立了**（这是本轮最大的一条偏离）

单据说：把「换时间词左边」那截喂给 `_pick_date`，得到的 ISO 就是"哪一条"，补上 `anchor_date` 就通了。
它 11-02（周一）实测的表：「把周二的健身房改到周六」→ anchor = `2026-11-03`，库里那条正好是 11-03 ⇒ 收窄命中。
今天 11-03（周二）再跑同一句：

```
'把周二的健身房改到周六'   左边='把周二的健身房'   _pick_date(左边)=2026-11-10   _pick_day(左边)=2
```

`_pick_date` 对「周X」算的是**下一个周X**（`planner.py` 里那句 `% 7 or 7`，注释还写着"今天就是周一的话也算，往后推满一周更符合直觉"）。
今天就是周二 ⇒ 它给 11-10，而屏上那条候选正是**今天** 11-03。`if _hit:` 落空原样退回 ⇒ **照样 many**。

所以"哪一条"这一维不能只用一个 ISO 尺度。补了第二把尺 `anchor_weekday`：**句子里有「周X」就按周几筛**，
没有（「11-04 那条」「明天那个」）才按那一天筛。两把尺的先后写进 `_hit_when` 一处，两个调用方共用。

### 0.2 只补 §2.2（不记账）走不完 §3.3 那五步 —— 记账不是可选项

单据 §2.4 自己写了：「周三那条」修完是"改问『11-04 那条，几点改到几点？』"。实测这一问就断在下一步：
他补「挪到周六晚上八点」，这一句里**没有名字**，只能靠上文捞出「健身房」→ 又筛出两条 → **还是列清单**。
循环只是往后挪了一步。所以这一支必须记住两件事：**列过哪几条**（顺序 = 屏上顺序）**+ 他第一句要改去哪**
（「把健身房挪到周六」里那个周六）。记下来以后，「周三那条」直接出卡，不必再问时间。

### 0.3 「改期缺细节」这个标记**只写不读**（这就是"改不动"的形状）

`grep -n "改期缺细节" app/main.py` 本轮改前只有一处 = 写它的那一行（`append_conversation(..., "改期缺细节")`）。
对照删课那一族：`删课缺细节` 有读回（`asking_remove`），所以删课的续答接得住。改期没有 ⇒ 续答没有主人。

### 0.4 单据 §一 那两行（参数现成、只有工具路在传）成立 ✅

`build_retime_existing_proposal` 的 `anchor_date` 与收窄三行都在（#87 磨的刀），
调用点只有 `propose_todo_change_tool` 递了它，确定性分支没递 ⇒ 本单第一刀就是"把参数递上"。

### 0.5 「第一条」能不能认？**能**，`_pick_todo_indexes("第一条")` → `[1]`（单据 §四.3 也是这么说的）
问题从来不在识别器，在**路由 + 记账**：`wants_retime_todo("第一条")` = False、`("周二的")` = False、
`("周三那条")` = False —— 这三句能进这一支**全靠语义层把它判成 retime**（他带 Key 才成立，实测就是这样循环的）。
没 Key 时这三句连分支都进不来。现在入口判据多了"这是不是在回答刚才那份清单"这一档，**不看模型也能走**。

### 0.6 两条我自己踩出来的坑（都不是单据里的，都补了判据）

| 坑 | 现象（实测） | 治法 |
|---|---|---|
| 形状不收紧就冤 | 「今天天气怎么样」带着「今天」，库里正好有今天那条 ⇒ 被点成"选它"并**出一张卡** | `pick_retime_candidate` 要求这句**除了日子/名字没别的内容**（擦掉后剩字就拒）；M8 钉 |
| 清单是上一轮的快照 | 那条被删掉后再回「第一条」，退回"按名字再筛"正好落在**另一条同名**上 ⇒ 卡指向隔壁那条 | 读回时验"这条还在库里"，不在就丢掉清单、下句重新列；M9/T20 钉 |

### 0.7 顺带纠正单据 §2.1 的方向

单据说"直接取整句会取到**新**日子"。实测**反了**：`_pick_date`/`_pick_day` 取的都是**最左**那个日子，
而中文里"哪一条"通常在左边 ⇒ 它列的六句**整句与左边同解**（M2 因此第一版是哑弹）。
真正会丢信息的方向是反过来那种语序 —— 「把健身房改到 2026-11-10，周三那条」（日子落在换时间词**右边**）：
取左边就拿不到日子 ⇒ 回到列清单。这个代价照实钉成 T28（它同时是 M2 的靶子），**不当成 bug 改**。

### 0.8 不治的（照单据 §四.3）

「11-04 那条」这种**月-日不写年**的说法 `_pick_date` 不认（`_DATE_ONLY_RE` 要四位年、`_CN_MD_RE` 要"月/号"）⇒
本单不治，落到列清单，用户可以回序号或说「明天那条」。

## 一、施工（planner 三处 + main 一处记账；`t_clean` 那张表**故意不动**）

### 1.1 planner.py

- `_RETIME_SPLIT_RE`：**从 `_RETIME_WORDS` 推出来**（`|`.join + `re.escape`），不另抄词表。
- `_hit_when(items, weekday, date)`：两把尺的先后（有周几只按周几；否则按那一天；都没给 → 空）。
- `pick_retime_candidate(todos, text)`：① 整句基本就是个序号 → **按传进来的那份清单**取；
  ② 纯指认日子（擦完日子和指代词后这句没剩字）→ 恰好筛出一条才算；③ 整句就是那条的名字 → 唯一命中才算。
  都不行 → None，**绝不兜到第一条**（越界也是 None）。
- `build_retime_existing_proposal` 新增 `anchor_weekday=0` / `pick_id=""`：
  `pick_id` 最硬（同名两条排在**同一天**时，"哪天"这一维分不开，只有 id 分得开 —— T5 实测那种数据），
  取不到就当没给；收窄那一刀从"按名字筛过"那一支**挪到外面**（不然「把周三那条挪到周六」这种没报名字的走不到），
  但引擎传来的 `anchor_date` 仍**只在按名字筛过时**才用（#87 那条保护：占位名 + 一个日子会把那天任何一条当答案）。

### 1.2 main.py

- `_pending_retime_list` / `_retime_followup`：many 那一支把 `(清单, 原话 want)` 记进暂存，
  unclear 那一支把 `(那一条, picked=id)` 记进暂存；读回两档都只看**紧挨着的上一句**
  （「改期缺细节」= 还在挑；「改期时间没说清」/「改期日子排不下」= 条已定，这句补的是新时间）。
- 入口判据多一档：`_rt_follow is not None and not _rule_veto`。
- many 那一支：清单**编上号**（`1. 2. 3.`，不编回「第二条」就没得数）+ 例子从候选现取（不再写死「周四那条」）。
- `_last_bot_message(session_id)`：「上一句 bot 说的话」这个判据全站收成一份（标记完成那一档原来就地抄了一份）。
- **一处字面没动**：`t_clean` 那张擦词表的词表。我第一版把它也接到 `_RETIME_SPLIT_RE` 上"统一一份"，
  实测把 #82补 F5 顶红了 —— 推出来的表多一颗「改改」，于是「周末改改」的残渣名字被擦干净、
  hint 接手、`empty` 变 `ok`。两张表**故意差一颗**，注释里写清了为什么（切句多擦一颗无害，擦名字多擦一颗改行为）。
