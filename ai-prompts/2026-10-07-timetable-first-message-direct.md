# 2026-10-07 上传课表：第一句话就直接出「修改课表」卡

## 1. 用户 Prompt（原话）

> 上传课表被当成了问事所有没有弹卡，第二次追问是代办弹了。直接改第一次修改课表

（承接 2026-10-06 那条 `confirm-render-race`——上一轮修的是"卡出了但被前端撤掉"，
这一轮学生说的又是另一件事：**根本没出课表卡**，而且追问一次反而弹了张**代办**卡。）

## 2. 研判：一句报障，两处病

把学生的话拆成两条可证伪的判据：

| # | 现象 | 判据 |
|---|---|---|
| ① | "被当成了问事" → 没弹卡 | 轨迹里写「🧠 我把这句听成 **问事**」 |
| ② | "第二次追问是代办弹了" | 第一句出 `timetable_change`、第二句出 `todo_add` |

**先真机复现，不猜。** 用 `/classify` 打那句 `timetableImportMsg()` 模板原话：

```
is_question=True   module=schedule   intent=chat   confidence=0.9   source=llm
```

——语义层（在线、有真实 key）**很自信地把"上传课表"判成闲聊问句**。
再看 `_rule_veto`（`main.py:1069`）：

```python
_rule_veto = bool(_need_review and _sem_intent and _sem_intent != _rule_hit
                  and (_asks or _sem_intent == INTENT_CHAT))
```

语义层一句 `chat` 就把规则层的"办事"否决掉了 → `_read_step` 写「问事」。
这就是 ① 的成因。

② 的成因是**分支顺序**：课表那一路原本只在**模型跑完之后**的兜底段（`main.py:3086` 起），
而所有"确认 / 待办补条"分支排在它前面。第一句被 `chat` 带走没出卡，
学生再问一次时，待办补条兜底就把话术里的「确认修改」当任务名捞走 → 弹代办卡
（跟 2026-10-03 那张"要不要把 确认修改 排进日程"的假卡是同一个坑）。

## 3. 决策：确定性硬闸门 + 提前到所有待办分支之前

两处病一副药——**规则层明说"导入课表"是硬信号，语义层猜的 `chat` 是弱信号，必须让位**；
并且这条分支要**排在所有待办分支之前**（"分支顺序本身就是判定"这条坑表再次命中）。

跟已有的 `physio_state_only`（生理状态句强制按 `chat` 走、不出卡）是**同款闸门**，
只是一个强制"问"，这个强制"办"。

三条自我约束：

1. **只有真能从文件原文抠出课程才出卡**。抠不出就照旧交给模型——
   模型还能替学生把"第几节"换算成钟点，那条路原样保留，不抢它的活。
2. **红线不动**：出卡 = 提案，`save_pending` 之后仍要学生点【确认修改】才写库。
3. **回话走同一个函数** `_tt_confirm_answer(n, "文件原文")`，
   免得"第一句直接出卡"和"模型出卡"两种走法说法不一致。
