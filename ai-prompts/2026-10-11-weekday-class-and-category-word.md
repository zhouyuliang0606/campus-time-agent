# 2026-10-11（晚些时候）· 三张截图打出来的两条链：读日子只认一种写法 + 类别词把整句判死

## 一、用户 Prompt 摘录

上一轮我给出施工顺序（过去时字段要先抽时间才能判），用户没回文字，直接给了三张真机截图：

1. 「每周6去图书馆」→ 回「好的，已取消，没有做任何改动。」+ 一张候选卡
   「📝 **6去图书馆** 这件事我替你看了几个空着的时间段」，四段是 周日/周一/周二/周三 —— **一段周六都没有**。
2. 「周六」→ 「好，那 **6去图书馆** 就定在 2026-10-17（周六）08:00-09:30」，一张**一次性**卡。
3. 「周6加个代办去图书馆」→ 「加待办缺细节」；「周六加个代办去图书馆」→
   「2026-10-17（周六）有空档，就是还不知道要加**什么事**——说一下事情的名字」。
4. 最后一张：候选卡整张的标题就是「**6去图书馆**」。

外加一句追问：「这样改完，你说的我工作日晚上7点背单词能稳定吗」。

## 二、研判

### 先回答那句"能稳定吗"

**判断稳了，内容还是错的**：`工作日晚上七点背单词` 谓词全成立（`clock_ok`、事名「背单词」），
但 `TimeSpec` 里"工作日"落不成任何字段，给的是一张**周一 19:00 的孤卡** ——
待办模型只有 `REPEAT_NONE` / `REPEAT_WEEKLY`+单个 `weekday`，表达不了"一周五天"。
两条路（摊 5 张卡走 batch / 给 repeat 加工作日档）都等拍板，没动。

### 截图 1 那句「已取消」不是后端答错

`student.html:911` 是点【取消】按钮的**前端回显**，只是排在用户气泡后面看着像答非所问。
措辞可以改得更不容易误读（列进未批项），但这一条不是判断缺陷。

### 真正的两条链

**① 读"周几"的地方只认一种写法（八处各自手写字符类）**
`_WEEKDAY_RE` / `_DAY_WORD_RE` / `_REPEAT_WEEKDAY_RE` / `_REPEAT_PHRASE_RE` / 两处擦标题 / 两处抠课名，
每一条都写死 `[一二三四五六日天]`。学生写阿拉伯数字时八处**同时**不认，于是：
周期丢 → 掉进摊候选那条路（那条路不 pin 日子）→ 擦标题只擦掉「每周」、把「6」留在事名上 →
**卡片标题印着「6去图书馆」**。这不是"再补一个词"能了事的，收成一份 `_WD_CHARS`（同红线 10）。

同批挖出**更早**的一条：`_WEEKDAY_RE` 连「星期X / 礼拜X」都不认 ——
「星期六去图书馆」日子读不出，`_pick_title` 还把**整句**当事名挂到卡上。

数字进来之后**新出现的歧义**（这是这次唯一需要设计的地方）：
「下周6点开会」「每周6点起床」里那个 6 是**钟点**。若跟着认成星期几，等于把"下周 + 6:00"
换成"下周六"—— 静默排错日子，比不认更坏。所以加了 `_WD_NOT_CLOCK`（`(?![点时:：])`），
四条出卡路共用。「每周6**次**」照旧归次数（14b 那条前瞻的阿拉伯版）；
「每周0」**不认**（0 是周日还是周一我们说了不算，宁可少认）。

还有一处会**抛异常**：`_pick_date` 里另写了一份自己数下标的
`"一二三四五六日".index(ch) + 1`（还先把「天」换成「日」）—— 「周6」一进来直接 `ValueError`，
整条链路崩。改成查 `_WEEKDAY_NUM`。

**② 类别词夹在句子中间，把整句判成"没说事名"**
「周六加个**代办**去图书馆」→ 系统反问「说一下事情的名字」。
判据链：`_strip_title_noise` 只擦**结尾**的类别词（`(待办|代办|事项|日程|时间)$`），
中间那颗留着 → `looks_like_thing` 拿 `_TITLE_NOISE` 做 `any(w in t)` → **整串**不算事名。
这正是上一轮刚写进红线 13 的那个机制（"往否决表加词 = 整串否决"）被真实句子打中的一次。
修法：类别词在中间也擦；否决表原样留着，它管的是另一种形状（擦完什么都不剩 → 才该问）。
副作用按住：`(?!表)` 保护「日程表」—— 「整理日程表」擦成「整理表」是"把名字改坏"，比问一句更伤
（「值日写作业」当初就是这么被投诉的）。

## 五、★ 顺带查出来的另一件事：测试读的是**真实样本库**，用户手测一次基线就变

加完 ② 之后全量从 7 条红变成 **9 条**，新红在 `test_01_basic`、`test_08_intent_fallback`，
输入都是同一句「图书馆几点关门」。用 HEAD 版 planner 做 A/B：**两条一模一样地红** —— 不是代码回归。

真因：`app/data/intent_samples.json` 里今天被真实测试灌进了四条含「图书馆」的样本
（`去图书馆`、`周6去图书馆`、`每周6去图书馆`、`我说的是周6去图书馆，你为什么瞎改`，intent 全是 `add_todo`），
而 `match_sample("图书馆几点关门")` 的 dice 相似度是 **0.444 ≥ 阈值 0.42** → 命中一条**事名为空**的样本
→ 一句提问被当成"要加待办但没说事" → 回「好——要安排的是什么事？」。

三个层次的问题，都还没获批：

1. **测试没隔离样本库**：`sandbox()` 不重定向 `intent_samples.json`（同 `todos.json` 那笔老账的另一半）。
   用户手测一次，全量基线跟着变 —— 这类"红"没法归责到任何一次改动。
2. **`match_sample` 的门槛形状**：相似度到了就接单，**不看命中的那条样本有没有事名**。
   空事名的样本至少该没资格抢判定（更严一点：提问句「…几点关门」这种带疑问词的，压根不该走 add_todo）。
3. **有一条是把吐槽学成了模板**：「我说的是周6去图书馆，你为什么瞎改」→ `add_todo`。
   这正是红线 12/13 一直在防的形状（学进去 = 把同一个错存成模板）。
   清它属于删真实数据，**要用户点头**；备份已在 `D:\campustime-scratch\bak-smoke-H\`。
