## 一、用户 Prompt（原话）

上一条修完之后，学生提了一个更根本的要求：

> **先自行思考，选择一个概率最大的是用户表达意思的去执行，这样可以吗**

接着：

> **更具上下文去判断加进去呢**

背景是他前面那句批注——**"去思考学生表达的意思，不是字面上的，要连接上下文猜测"**。
他要的不是"加词"，是**判定层别只看当前这一句**。

AI 的回答是：「可以，但"猜"必须有个前提——**猜出来的东西只能是一张提案**，
不能直接执行。红线（执行权在系统、学生点头才动）不因为"猜得更准"而让步。」

## 二、AI 研判

### 1. 「猜概率最大的」什么时候成立

删除**不可逆**，猜错代价学生承担不起。所以不是"猜得更准"，而是**只在猜错也无所谓的地方猜**。
把判决排成四级阶梯，越往下越不确定：

| 档 | 情形 | 做法 |
|---|---|---|
| ① | 唯一命中 | 出确认卡 |
| ② | 是"哪一条"的**回答**（报序号/回名字） | 按上下文解析 |
| ③ | 候选里有一处**结构性事实**让答案确定 | 替他挑 + **写明依据** + "换一条"出口 |
| ④ | 说不清（平局） | 列清单，绝不猜 |

第 ③ 档就是这次实现的部分，只认两处**结构上确定**的事实，**不做相似度猜测**
（0.31 比 0.29 是噪声，按"最像"下结论只会给学生**假确定**）：

- **S1 精确命中**：名字**正好等于**某条标题的只有一条（《游泳》与《游泳锻炼》都在库里，说"删掉游泳"→ 就是《游泳》）；
- **S2 等价组**：同名＋同日＋同时段＋同状态 → 删哪条学生看到的日程都一样，**不存在"猜错"**；挑**先写进去的那条**，并把另一份的 id 放进 `alternates`。

### 2. 一个自踩的坑（已修）

一开始把这两处证据的判决放在"点了名"这道闸门**外面**，结果「删除撞时间的代办」
（只给筛条件、**要删几条都还没说**）直接出卡，把后面的「每个删一个」全抢走了
（`test_12` 一次挂 5 项）。

判据改成两处证据都必须挂在 `if by_name:` **里面**——他连"要删几条"都没定的时候，
替他挑一条比不猜还糟。

### 3. 真机实测**新发现**的 bug：语义层抢单

这次不是学生报的，是我按惯例在真机上把整条链路走一遍时撞见的：

```
上一句：你说的这条对上了好几条待办…（列 6 条：游泳×2 交电费×2 晨读×2）
我：游泳          ← 在点名
系统：✅ 你说的这条对上了好几条待办，我不敢替你挑（标记完成清单）
```

**根因**：`app/main.py` 里标记完成分支（3h）排在删待办分支（3g）**前面**，而**语义层**
只看「游泳」这两个字，判成了 `done_todo`（光看这俩字，确实更像"办完了"）——
这句被 3h 接走，判定层再怎么按上下文解析都**没机会跑**。

**判据分强弱两层，只让弱信号让位**：

| 信号 | 来源 | 处理 |
|---|---|---|
| "把游泳**标记完成**/勾掉" | 规则层（词表）**明说** | 硬信号 → 标记完成照旧接 |
| 「游泳」俩字被判 done | 语义层**猜**的 | 弱信号 → 让给删待办 |

实现上：把 `held_now` / `answers_held` / `asking_rm_todo` 的判定**上移到 3h 之前**，
3h 的入口闸门加 `and not (_rm_reply_pending and not _done_hard)`，3g 直接复用同一批判据
（同一个判据两处各算一遍，将来改一处就会悄悄不一致——这类 bug 的老家）。

### 测试写法上的一个关键点

`test_14` 必须**把语义层替成一个假货**（"见名字就判 done"）才测得出来：
沙箱里没有密钥，**真实语义层是静默返回 None 的**——不替，
这个 bug 在测试里永远看不到。这就是「**测试全绿、真机照样错**」的来源。

替的时候要打补丁到 **`app.main` 这个模块的名字上**，不能打 `app.agent.intent.classify`：
模块顶部的 `from X import Y` 是**导入时绑定**的，换原模块里的函数看不出来
（这个坑本项目踩过：语义层于是"安静地"退回关键词表，异常还被 `except` 吞掉）。

### 2. 跨过午夜后多出的 5 项红：全是**断言写死日期**

清完数据复跑，发现失败从 14 项降到 5 项，但**多了 `test_03` 这个新面孔**。
没有直接改，而是按"**别凭直觉认领别人的锅**"走了一遍：

1. 用**老代码工作树**（`git worktree add ... ef62114` + 把 `app/data` 补进去）跑同样两个文件
   → 红项**逐条一致**（同 3 项 + test_03 那 2 项）⇒ **与本轮功能改动无关**。
2. 写探针确认**产品行为其实是对的**：今天 09-30（周三），`_pick_date("周二")` → 10-06，
   卡也正确落库成 `游泳 2026-10-06 16:00-17:30`。
3. 结论：断言里钉着 `2026-09-29`（写它时的"周二"），**过了那天就永远红**。

四处一起改成"跟着今天走"，且**只改日期来源、不放松守卫**：

| 位置 | 原来 | 改成 |
|---|---|---|
| `test_03` 按月聚合 | `mon = 今天所在月` | `mon = tmr[:7]`（**跟着明天取**——月末那天两者不是一个月） |
| `test_03`「今天至少 1 项」 | 假设"演示数据今天正好有安排" | 自己种一条今天的再断言它出现在月表里 |
| `test_06` 第五批 | `date == "2026-09-29"` | 断言**意图**：候选同一天、且那天是周二 |
| `test_06` 第十一/十二批 | 查写死的 09-29 / 09-28 | 查**卡上那一天**（`card["date"]`） |

> 教训：**测试里凡是出现字面日期，都要问一句"这个日期是怎么来的"**——
> 程序按"今天"算的，断言也必须按"今天"算；否则它会挑**月末**或**隔天**这种
> 最不该出事的时候变红，看起来像刚改坏的。判据很简单：**老代码跑一遍，
> 红项一样 → 不是你的锅**（这一步花两分钟，省一整轮瞎改）。
