## 三、执行过程：两次失败 + 一次成功

### 尝试 1、2：`git filter-branch`（失败）

```
FILTER_BRANCH_SQUELCH_WARNING=1 git filter-branch -f --env-filter '...' -- master
```

| 次 | 结果 | 观察 |
|---|---|---|
| 1 | 空输出后 SIGTERM | 连 "Rewriting commits" 都没打印，怀疑多行参数被吞 |
| 2 | 跑到 85/194 被杀 | 输出显示 **~3.3 秒/提交**，194 个要 **11 分钟**，必然撞时间上限 |

**关键观察**：`filter-branch` 每个提交都要起一堆子进程，在 Windows + Git Bash 上开销极大。
两次都在中途被杀，但**仓库均未被破坏**（提交数、哈希、身份原样，`refs/original` 未生成），
只有 `.git-rewrite/` 残留目录——`mv` 挪走即可（沙箱里删除会卡，改名不卡）。

### 尝试 3：`fast-export | 改写 | fast-import`（成功）

单遍流式重写，不按提交起子进程，**秒级**完成。

```bash
git fast-export --no-data --reencode=no master > stream.raw
sed -E 's/^author .* <[^>]*> ([0-9]+ [+-][0-9]{4})$/author zhouyuliang0606 <3215477176@qq.com> \1/;
        s/^committer .* <[^>]*> ([0-9]+ [+-][0-9]{4})$/committer zhouyuliang0606 <3215477176@qq.com> \1/' \
    stream.raw | git fast-import --force
```

**两个刻意的设计决定**：

1. `--no-data`：流里不输出文件内容，改用「按原 SHA1 引用已有对象」。
   于是整个流**纯文本、只有 216K**，用 `sed` 做文本替换就**不存在误伤二进制文件内容的可能性**。
   代价是这份流只能在**本仓库**里导入（对象都在）——正是我们的场景。
2. 正则**收紧到行尾**：`^(author|committer) .* <[^>]*> [0-9]+ [+-][0-9]{4}$`。
   故意要求「时间戳 + 时区」结尾，避免误伤提交说明或文件内容里恰好以 `author ` 开头的行。

**执行前先空跑核对**：

| 核对项 | 结果 |
|---|---|
| 流大小 | 4055 行 / 216K |
| 命中待改行数 | **388** = 194 提交 × 2（作者 + 提交者）✅ |
| 原始身份分布 | 188 `zhouy <zhouyig@163.com>` + 6 `zhouyuliang0606 <312324985+…@users.noreply.github.com>` |
| 含 `author`/`committer` 开头但**不匹配**的正则行（潜在误伤） | **0** |

## 四、验证：怎么证明「换人没换内容」

这是本次最关键的一环。**只报「194 个提交都改名了」是不够的**——必须证明文件内容没被动过。

| 验证项 | 期望 | 实测 |
|---|---|---|
| 提交数 | 194 | **194** |
| 作者身份 | 194 全为 `zhouyuliang0606 <3215477176@qq.com>` | **194 / 194** ✅ |
| 提交者身份 | 194 全为同一身份 | **194 / 194** ✅ |
| **每个提交的树对象 + 提交说明** | 与备份仓库**逐条相同** | `diff` **完全一致** ✅ |
| 工作区 | 干净 | `clean` ✅ |
| 提交日期 | 原样保留 | `2026-09-27 17:25:24 +0800` ✅ |

> 「树对象哈希」是 Git 对「整个目录快照」算出的指纹。194 个提交的树对象与备份**逐个一致**，
> 等价于**证明文件内容零改动**——比 `git diff` 更强（diff 只能比两个端点，这里比了全部 194 个）。

**安全网**：改写前已做**整仓镜像备份**（`backup-campustime-git-20260927.git`，194 提交、HEAD `e42a9ff`，
与工作仓库校验一致）。任何环节出问题，一条 `git clone` 即可回滚。

## 七、推送与验收

重写完成后，用「令牌内嵌 URL + **显式租约**」强推上线：

```
git push --force-with-lease=refs/heads/master:<远端原哈希> \
    "https://x-access-token:***@github.com/zhouyuliang0606/campus-time-agent.git" master
```

> ⚠️ 推 URL 时 `--force-with-lease` **必须把期望的远端哈希写死**——没有 remote 名就没有
> remote-tracking ref 可参照，不带值等于失效。好处是 **fail-closed**：远端若已变，直接拒绝，不会误覆盖。
> 令牌只存在于仓库外的临时凭据文件里，**不进仓库、不进 `.git/config`**。

## 八、这次踩到的坑（供后续复用）

1. **`filter-branch` 在本机不可用**：~3.3 秒/提交，Windows 上必被时间限制杀掉。
   要改历史，用 `fast-export | sed | fast-import`，秒级、单遍、可控。
2. **`--no-data` 是安全关键**：不把文件内容灌进流里，文本替换就不可能误伤二进制；
   且能顺带避免 `sed` 在二进制数据块里「恰好撞上」`author ` 开头的行。
3. **正则必须收紧到行尾**：靠「时间戳 + 时区」结尾锚定，把提交说明/文件内容排除在外。
4. **改完必须验「树对象逐个一致」**：光看「身份都改了」会漏掉「内容被改坏」这类事故。
5. **沙箱里删目录会卡**：残留的 `.git-rewrite/` 用 `mv` 改名挪走，不要 `rm`。
6. **改历史的连带成本要提前算**：哈希引用、演示视频分镜里要现场执行的 `git show`，
   都属于「改了历史就顺手改坏」的地方，必须一起同步。
7. **改完配置要立刻回头验，别凭「我执行过」就当成功**。本次真实踩到：同一轮里把仓库级身份改好、
   顺手读了全局身份，却在汇报里写成"全局也一并改掉了"——实际只读没写。隔了一轮核对时才发现
   `global` 仍是 `zhouto`/`zhouyig@163.com`。**教训：配置类改动，改完必须再读一次确认，
   并把读到的值本身作为证据贴出来**（「我以为改了」和「我读到它已变」是两件事）。
