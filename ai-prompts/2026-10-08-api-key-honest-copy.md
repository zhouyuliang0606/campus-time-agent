# 2026-10-08 P0-4：API Key 那句谎——「不会上传服务器」和「不落盘」是两件事

## 用户 Prompt（摘录）

> 4. API Key 伪脱敏：student.html:2627 文案说"密钥不上传服务器"，但 :1736 每条聊天都把
> 含 api_key 的 model_config 发到 /api/chat。修复：如实改文案（或改前端直连模型），
> 服务端不落盘密钥。

## AI 研判与决策

先把这一条**拆成两个独立命题**，因为它们一个为假、一个为真，混在一起修会修错方向：

| 命题 | 实际 | 结论 |
|---|---|---|
| 「密钥不上传服务器」（前端文案） | `student.html:1733` 每轮对话把整份 `{base_url, model, api_key}` 塞进 `/api/chat` | **假**，改文案 |
| 「服务端不落盘密钥」 | canary 灌进真接口，逐文件扫数据目录：零命中 | **真**，但要变成跑出来的证据，不能停在"读代码看起来没有" |

谎话的**源头在服务端注释**：`app/config.py:42` 的 docstring 写着
「override 是学生端…（仅存本机浏览器）」，`app/main.py:999` 同一句，前端照抄成用户看得见的承诺。
同一个错长成三份，所以三处一起改口——只改前端那句，下一个人还会从注释里再抄一遍。

**为什么不选另一个方案（前端直连模型）**：这套 Agent 的循环在服务端跑
（`app/agent/engine.py` 要拿工具执行结果再回问模型，ReAct 好几轮），直连等于把循环搬进浏览器重写，
还要各家模型厂商各自处理 CORS。而且服务器持有工具与数据，密钥直连也省不掉服务端持钥这条路。
**"密钥会经过服务器"是这套架构的固有代价**，那就把它写清楚，并给出退路（不填就走管理端默认模型）
与风险提示（演示走明文 HTTP，同网段抓包看得见）。

顺带查清并**确认没问题**的三件事（查过不等于以后没问题，所以都进了护栏）：

- 密钥不会串：`get_llm_config(override=...)` 每次调用现读，`DeepSeekClient._config()` 把 key 取进
  局部变量、`httpx.AsyncClient` 每请求新建，网关实例随请求产生——两个学生各用各的。
- 管理台不会看到学生的 key：`GET /api/admin/settings` 读的是服务器配置（不带 override）。
- 管理侧那把**按设计落盘**在 `app/data/settings.json`（在 `.gitignore` 内），和学生的"用完即弃"是
  两套语义。这个区别写进测试注释，免得后人"统一一下"把哪一边改坏。

### 挖出来的一条真问题：失败路径会把 key 写进账本

`gateway.py` 原本 `err = str(e)[:300]`，而 `err` 会**原样进 `llm_usage.jsonl`** 的 error 字段——
那张账管理台能读、也可能被贴进评审截图。各家 SDK 的报错爱把请求上下文拼进异常文本
（URL、甚至 header），一旦带上 `Authorization: Bearer sk-…`，"不落盘"的承诺当场作废，
而且是**静默作废**：只有失败的那几次会写，正常演示看不见。
所以加了 `_redact()`：**先把密钥抹掉，再截断**。顺序是关键——先截 300 可能正好把 key 切成半截，
半截匹配不上原始串、又够被人拼回去（C2b 就专门把 key 压在 300 边界上验这一条）。
取的是 `get_llm_config` 生效那把，不是 override 本身：学生没带 key 时该防的是服务器自己那把。

**为什么留了 base_url**：失败文本里 `连不上大模型服务（http://127.0.0.1:1/v1）` 这种地址照旧落账。
这不是漏——管理员要靠它判断"学生连的是哪个地址"。C4 把"允许"钉成断言，
免得下一轮有人"顺手也脱敏掉"，把诊断能力换成了查不出问题的日志。
