## 一、决策 ① 驿站页面要不要列学生登记的条目 → **要列** ✅

**拍板：列。**

理由：
1. **驿站就是"运营台"**——学生登记进来的东西（失物招领、报修…）管理员**看不见就没法处理**，那这项"服务"就是个黑洞。
2. **读接口已有**（`custom_records` 读接口），只差界面 → 成本极低。
3. **能演示创新**：*"学生登记一条 → 驿站端立刻看到"*，正是"服务找人 / 自生长"那张饼的可见证据。
4. 与"接活"一致：驿站本来就该看到学生递过来的东西。

落地建议：驿站端加「📋 学生登记条目」列表，**按服务分组**（读 `custom_records.json`）；只读展示，若服务定义了状态则可改状态。

## 二、决策 ② 自建"宿舍报修"让不让接走"报修" → **让**（自定义服务优先）✅

**拍板：让自定义服务接走。**

### 病根（实核）
- `_WORK_ORDER_RE`（`planner.py:1674`）最后一条 alt 是 `|报修` → 任何含"报修"的话都判成工单。
- 自定义服务匹配在 `main.py:1495`（**确实排在工单分支之前**），但工单硬分支 `main.py:1581-1591` **没有被 `is_custom_module` 守门** → 前面就算把 `module_key` 改成了 `custom:<宿舍报修>`，1591 照样劫持、弹通用上报卡。**所以自建服务接不走。**

### 修法（一行守卫）
```python
# 2.6) 快递/外卖丢失破损 → 上报卡（main.py ~1591）
_wo_kind = looks_like_work_order_report(message)
if _wo_kind and not is_custom_module(module_key):   # ← 加这半句
    ...
```

### 依据（就是你们自己的红线）
Qoder 刚立、刚落库的 **红线 21**（`4e30cc3`）：**"硬信号只许'没人接管时'接管"**。
工单硬分支是**通用兜底**，自定义服务是**用户明确定义要接管这句话**的 → **specific 应优先于 generic**。加这半句正是执行红线 21。

### 不受影响 / 安全
- 快递/外卖丢失破损（**没有**自定义服务接管）→ 照旧出上报卡，行为不变；
- 卡片 + 系统写库的地基不变（自定义服务也是"出卡 → 学生确认 → 系统写"）。
