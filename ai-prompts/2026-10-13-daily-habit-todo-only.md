## 二、开工前实测：施工单的三条前提，两条不成立

| 施工单说 | 实测 |
| --- | --- |
| §三.1 从 `_UNSUPPORTED_PERIOD` 摘掉「每天/天天/每日」就彻底放开 | **不成立**。摘完之后 `wants_add_todo("我每天都要背单词")` 仍是 `False` —— 拦它的不是否决表，是**接单开关根本没有 daily 这一档**（weekly 那条是 2026-10-10 单独加的）。只照它改会得到"不拦了，但也没接"：卡一张都不出，学生只看到一句通用废话。两处都改了，并用变异 Y2 钉住这种半修。 |
| §四 `list_todos` / `list_todos_in_month` 不用改 | 半对。`list_todos` 确实不用改；但 `list_todos_in_month` **就是**日历月视图的取数处（逐天问 `todo_occurs_on`），daily 在那儿天天返回 True → 月表每天一格都是它。按用户第 2 条决定，在这**一处**滤掉习惯，而不是叫 `todo_occurs_on` 撒谎。 |
| §四 只列了 `todo_occurs_on` / `todo_done_on` / `add_todo` 三处 | **漏了第四处**：`set_todo_done_on` 里那句 `if repeat == REPEAT_WEEKLY`。漏掉它的后果是"勾掉今天"会去翻整条 `status`，明天这条就没影了 —— 正是施工单自己在 §四 里反复强调不许发生的事。 |

`repeat` 相关的判断散在**六个地方**（planner 四处 + store 两处 + 前端两份），所以这一轮顺手收敛成三处判据：

```
store.HABIT_REPEATS      → 这条是不是习惯（日历画不画）
store.DAY_LOGGED_REPEATS → 这条的完成按不按天记
planner.repeat_of(text)  → 这句话该落哪一档 repeat（weekly 优先，其次 daily）
```
六个调用点现在都只问这三句。加下一档（比如「工作日」）不用再去改六个地方。

## 三、真机上查出来的老洞：「说出来勾掉」是空操作

给习惯做完之后，我按 §7 的验收单去勾今天，结果**勾不动**。往下挖发现不是 daily 的问题，
`weekly` 也一样中招（所以它比 02 更早）：

```
建一条 daily → POST /api/chat「背单词完成了」→ 出卡 → 「确认」
   改之前：status='done'  done_dates=[]  →  todo_done_on(今天) = False   ← 白勾
   改之后：status='planned' done_dates=['2026-10-13'] → True
```

病根：读侧对 `weekly/daily` 一律只看 `done_dates`（`todo_done_on`），
而两条确认路径（聊天里说"确认"、以及确认卡发的 `PUT` 不带 `on`）写的却是整条 `status`。
**写一个没人读的字段**，现象就是"我明明勾了，明天它还在"。

修法：
1. `store.set_todo_done_on` 对按天记的那一档**不传日子也按天记**，退到 `done_date_for` 算出来的那天
   （今天算出现就记今天，否则记锚点，不把完成记到一个没安排过的日子）；一次性待办行为一字未变。
2. `PUT /api/todos/{id}` 那道闸从 `if on and "status" in body` 改成 `if "status" in body`，
   分流交给 store 那一处，入口不再自己判档位。
3. 回执话术跟着改：习惯勾一次要说清「{今天} 这一勾已记下，明天它还会出现」。
4. **同一个病的另一面**：排空档时算"这天被占了没"用的是 `t["status"] == "done"` ——
   对习惯永远不成立，于是学生今晚把单词背完了，系统还把 21:00-21:30 当成占着、另给他挑时间。
   改成问 `todo_done_on(t, date)`（判据一份），Y12 变异盯着它。

## 四、"不画进日历"落在哪：滤在取数处，不叫判据撒谎

后端：`list_todos_in_month`（月视图取数）滤 `is_habit`。
前端：`todoOccurs` **保持说真话**（daily 天天都算在），只加一个 `isHabit(t)`；
日历那三个渲染点（周表 / 月表 / 选中日下钻）各写成 `!isHabit(t) && todoOccurs(...)`，
两份页面一共六个点，测试按**计数**钉（少一处就是习惯钻进格子）。
代办清单和红角标继续用没滤的 `todoOccurs` —— 它数的正是"今天还要打卡的条数"。

红角标在侧栏和代办标题各一颗；窄屏（<720px）那条 `.sb-item span:not(.ico){display:none}`
会把角标一起藏掉，所以补了一条**写在它之后**的例外规则（手机上最该看的恰恰是这个数）。
`confirm.html` 的候选卡对 `daily` 单加一条说明：不写"只进代办清单"，学生勾完在日历里找不到，
只会判成"系统没记上"。

## 七、遗留（等拍板 / 等下一轮）

- **「一周 N 次」落成一条习惯** —— 方向用户已定（第二节第 1 条），本轮没做。
  它要同时回答三件事：一条记录怎么表达"每周七次"、这周算不算做完、
  以及 `test_35` 钉着的"这一周铺 N 条"要不要退役。实测口径现在是不一致的三句：
  「一周三次」放行铺 N 条 / 「每周背三次单词」被 `unsupported_period='每周背三次'` 拦 /
  「每周要背七次单词」被 `unsupported_period='每周要背七次'` 拦。
- **红角标只有代码层证据，没实拍。** 本轮我验的是 DOM 结构与显隐写法（inline 写死、窄屏那条例外规则
  排在隐藏规则之后、选择器权重够不够），**没有真在 720px 以下的窗口看过一眼**。
  按这个项目定下的规矩（视觉判断要拿实物样张），这一格得由用户自己瞄一下或让我补拍。
