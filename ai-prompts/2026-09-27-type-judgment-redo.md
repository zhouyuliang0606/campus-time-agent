# 2026-09-27 类型判定整体重做：先分「问 / 办」，语义优先、关键词兜底

## 用户 Prompt（原话）

> （承接上一条：「校园问答这一栏，我是想让他去知识库找的，变成添加代办了」）
> **你只是修了这一个，其他类型的区分没改**

随后我在两个选项上征询：
1. 「类型判定怎么改？」→ 用户选 **「类型判定整体重做（推荐）」**
2. 「语义层可以调 LLM 判类型吗？」→ 用户选 **「允许，且规则兜底」**

## AI 研判

上一轮（`2026-09-27-campus-qa-kb-routing.md`）只做对了一半：
`_GO_QUESTION_RE` 是**给一句话补的一道闸门**，类型的**判定方式**没动过。当时的病根其实有三层：

1. **"归哪个模块"和"想干什么"分在两处判，互不通气。**
   `router._QUICK_MAP` 是 50 多个 `if keyword in text` 的子串匹配，
   `main.py` 那条加待办分支是 30 多张表的关键词链——两者各判各的。
   于是"看见『取快递』就归快递模块"和"这句话要不要排时间"之间**没有任何协调**。
2. **3c 加待办分支不分模块**，所以前端锁 `module=faq` 也拦不住它。
3. **规则与语义层没有统一的仲裁规则**：原来只在 `add_todo + 旧查询词表` 这一种组合下复核，
   换个说法（比如「安排个时间去快递站怎么走」——没有任何旧词表里的字）就直接出卡。

结论：要动的不是词表，是**判定层的结构与优先级**。
于是把「类型（module）」也收进判定层，和「意图（intent）」做**同一次判定**，
顺序由"关键词第一"倒成"**语义第一、关键词兜底**"：

```
① 样本库（零成本、离线、越用越准）
② 语义层 LLM：一次输出 {module, intent}，只读分类，碰不到任何执行接口
③ _QUICK_MAP 关键词兜底（没配 key / 调不通时才轮到它）
④ 还不行 → faq：答一句总比替学生办错事安全
```

**判定层与执行层的红线不变**：模型仍然只吐字段（谁也没给它写库接口），
查空档、摊候选、出卡、写库全部在 `planner.py` 那套老代码里执行。

## 关键决策（含一次自己踩出来的回归）

- **先分"问 / 办"，再定类型。** 新增 `QUESTION_RE` + `looks_like_question()` 作为**粗信号**，
  只用来决定"要不要升级到语义层复核"，**绝不用它下结论**（多义词是子串匹配的天生盲区）。
  语义层的 system prompt 里把这条写成硬闸门：问句一律 `chat`，且**绝不算 add_todo**。
- **否决闸门收窄成两种"正面肯定"**（宁可漏判，不可替学生办错事）：
  这句话本身带提问信号，**或**语义层明确说 `chat`。
  刻意**不采纳**"只要和规则结论不同就否决"——样本库是模糊匹配，
  误否决一张本来就该出的卡（"帮我安排周二的游泳"）比漏判更让学生恼火。
- **踩到的回归（已修）**：语义层那条路会把口语翻成规范话
  （`to_canonical`：`{"title":"游泳","minutes":0}` → `"加个游泳"`）再喂给老解析器。
  可规范话是**拿语义字段拼的**，字段里没有的信息会整段丢掉——
  「帮我安排周二的游泳」里的"周二"一丢，候选时段就摊到一整周去（`test_06` 实测红）。
  改成**只在规则读不出来时**才用规范话兜，规则认得的句子照旧拿原话解析。
- **踩到的坑（已修）**：`Router.__init__` 原来在实例化时就建死客户端，而
  `from app.llm.client import DeepSeekClient` 是**导入时绑定**的，
  导入后再打桩/换配置都传不进来——测试里"语义优先"会**悄悄退回关键词表**，
  而且是安静地退（异常被 `except` 吞掉）。改成按需注入、不注入就交给判定层自己建。
- `MODULE_MEANING` / `DEFAULT_MODULE` / `module_hint()` 只写一份：
  此前 router 自己抄了一份 module 说明，改一处忘一处。

## 补充：把学生界面上那两张残卡清掉

学生随后把他界面上挂着的两张卡原样报了回来，并补了一句设计取向：

> 刚才系统给你挂了两张待办确认条（「**哪取凯迪**」「**哪取快递**」），那其实是你问路的话
> 被误当成待办事项了，不用点确认，忽略掉就行。取快递这事不需要排进日程哈。
> **先区分，再选择**

**为什么"两张"只找得回一张**：两张卡是同一个浏览器会话先后产生的，而后端暂存
（`app/agent/pending.py`，落盘 `app/data/pending.json`）是**按 session_id 存一条**——
第二次把第一次覆盖了。所以「哪取凯迪」在暂存里已经不存在，只剩「哪取快递」；
而**两条都在 `sessions.json` 的聊天记录里**留着（那是会话历史，不是覆盖式的）。

**它们为什么"关了页面还会回来"**：前端 `sessionId()` 把会话 id 存在 `localStorage`
（`campustime_session` / `campustime_session_<view>`），于是下次打开同一个栏目，
`/api/conversation/<sid>` 会把那段带残卡的聊天读回来、`peek_pending` 又读到那张还没确认的卡
→ 确认条重新挂出来。**而且这时随手回一句「确认」，就会把「哪取快递」真写进日程。**

**清理（都属 runtime 状态，两处都已在 `.gitignore` 里排除）**：
1. `app/data/pending.json`：清空。里面 15 条全是过期卡/探针卡（含 3 处「哪取快递」），
   没有一条是学生正在等的。
2. `app/data/student/sessions.json`：摘掉带残卡的那个会话 `s793487017d`（6 条消息）。
3. **必须重启后端**：暂存是内存态（`_ensure_loaded()` 只在"数据目录变了"时才重读盘），
   不重启的话内存里那份旧副本照样会把残卡挂出来。
4. 真实日程**没被碰过**（清完仍是 4 条干净数据）；清理前把两份文件备份到仓库外
   `backup-campustime-removed-junk-20260927/`（备份不进仓库，避免误提交）。
5. 顺手查了**样本库** `app/data/intent_samples.json`：15 条全是真样本，
   没有把问句误学成 `add_todo` 的污染（这一点很关键——现在语义优先，
   一条被误学的样本会直接把错误判定复活）。

**"先区分，再选择"落到代码与测试上**：先分"这是问还是办"，再决定"答它还是排它"。
两句原话（含错别字「凯迪」）现在钉了永久回归：离线上 `wants_add_todo` 为假、
`_rule_intent` 为 None；在线（语义层说 chat）端到端一张卡都不出。

真机验收：残卡会话的聊天记录已空；对它回「确认」→ 系统如实说
"你确认的是哪件事？我这边还没给你出过确认条"（没有写脏数据）；
「我要去哪里取凯迪」→ 知识库反问澄清，「我要去哪里取快递」→ 知识库答快递点位置，两者都无卡。
