  ⇒ 该补的是：15 / 18 / 22 / 24 / 25 这一族 drop-in **原文照入**，命名沿用 `2026-MM-DD-<英文主题>.md`，一字不改。

## 二、新决策：登记条目要不要「处理状态」

**Qoder 抛出的原话**：服务定义里没有状态字段，所以登记条目不给改状态按钮 —— 要改得先给定义加状态。

**现状实核**（不是猜）：

```
app/store.py:1038  item = {"id":…, "ts":…, "service":…, "name":…, "fields":…}   ← 没有 status
app/store.py:123   update_workorder_status(wo_id, status)                        ← 工单有，改法=读全量→改一条→整份写回
app/main.py:3978   _workorder_status_response(wo_id, body)   ← 状态校验的**唯一实现**
app/main.py:3985   if status not in _WO_STATUSES: → 400 "status 只能是 待处理/处理中/已解决"
```

工单那套已经跑通：**三态 `_WO_STATUSES`、一份校验实现、管理端与驿站端共用**（3981-3982 的注释就是为防"两份状态表"写的）。

### 选项 A（我建议）：加，但**只加一个系统级 status，词表与工单共用**

- 结构上照抄工单：`add_custom_record` 落库时**由系统**写 `"status": "待处理"`；老记录没有这个字段 → 读侧一律 `w.get("status") or "待处理"` 兜（**不批量迁移文件**，那条会动真实台账）。
- 校验**复用 `_WO_STATUSES`**（main.py:3985），不新开白名单 —— 这就是红线 21 的"判据只许一份"。
- 前端复用现有 `WO_NEXT`（station.html:235）与 `.st / .st.doing / .st.done` 三档样式（94-96 行），驿站端两块表**同一个函数、同一个词表**，不出现"工单叫已解决、登记叫已处理"这种自己都对不上的情况。
- **状态不进 `collect_fields`**：它是**流程**不是**内容**。让模型按管理员那句话生成状态词，等于 N 份服务定义各带一套状态表，前端还得写 N 套逻辑 —— 这是本仓吃过几次的病。
- 边界划在"只改状态"：**不做删/改登记内容**，本轮到此为止，免得把低代码一口气做成完整工单系统。

**为什么值得做**：用户自己建的正是「**电梯报修**」这类服务 —— 报修登记完，管理员在页面上**没有任何"处理完了"的动作可做**，演示时问一句"然后呢"就卡住了。这也是"驿站=运营台"这条线唯一的缺口。

### 选项 B：不加（保持只读记录）

低代码的卖点是"说人话就能建一项服务"；加状态 = 把"服务定义"升级成"流程定义"，超出创新描述锁死的范围。
那就按 Qoder 的意思写进 EXPLAIN 六，明说"登记条目只读"，演示时主动讲这是有意的取舍。

### 两段 EXPLAIN 六 可粘文本（按拍板选一段）
