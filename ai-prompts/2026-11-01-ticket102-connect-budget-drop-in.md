### 0.4 为什么 3 秒不够：一次丢包重传就能吃掉它

`:311` 那段注释写的是：

> connect 仍 3 秒 —— 「这台机器连不连得上」这件事不该因为流式就变慢。

这个想法本身没错，但**它默认了「连得上」是几十毫秒的事**。实测（§0.2 单量握手那一行）：
**冷连接 481~909 ms，热连接 101~141 ms。**

冷连接 = TCP 三次握手 + **TLS 握手（还要 2 个来回）**，一共 3~4 个 RTT。国内到 `api.deepseek.com`
一个 RTT 约 30~100 ms，所以 0.5~0.9 秒是正常值、不是慢。

**关键在于 TCP 丢一个包不是加 30 ms，是退避重传：200 → 400 → 800 → 1600 ms。**
握手阶段只要丢两个包（Wi-Fi 上很常见：漫游一下、路由器忙一下、Wi-Fi 休眠唤醒），
冷连接就会从 0.6 秒变成 **1.4~3.4 秒** —— 3018~3048 ms 这一簇正好压在 3 秒线上，
说明当时是**差一点点就进去了**，不是"根本没有网"。

⇒ 3 秒这个预算只够扛**一次**丢包重传，扛不住两次。这就是它偶发的原因。

### 0.5 为什么偏偏「上传 Excel」最容易撞上

导课表是**全项目最长的一条链**：`client.py` 顶部注释自己写着「一句『食堂几点关门』要走三次模型往返
（判定 + 引擎 + 带工具再想）」，导课表比它更长（还要 `read_uploaded_file` + `propose_timetable_change`）。
而连接池是 `keepalive_expiry=30.0`（`:56`）：

- 学生点「上传课表」→ 上传（本地解析 xlsx，**不花模型**）→ 前端发 `timetableImportMsg`
- 这中间有几秒空档；**超过 30 秒就一定是冷连接**
- 一次导入要连 3~4 次；只要其中一次撞上冷连接丢包，整条链就断在一句话上

所以不是 Excel 有毒，是**这条路要连的次数最多、冷连接的次数也最多** ——
每多连一次，就多一次"3 秒内握不完手"的机会。

### 0.6 还有第二种「连不上」，本单**不修**但要记下来

历史上还有 `read` 超时的同族（不是 connect）：

### 0.7 ⚠️ 23:08 之后再查，**同一个 bug 又多了一张脸**（本单必须一起治）

用户接着报「让他自我介绍，也会卡」。再看流水，同一小时的失败换形状了：

```
23:08:23 ~ 23:09:46   3022 / 3023 / 3027 / 3030 / 3037 ms  ×7   ← connect 用完（老样子）
23:09:58 ~ 23:11:07   6017 / 6016 / 6007 / 6005 ms        ×4   ← 正好 2×3 秒
23:11:32             24395 ms                             ×1
```

**6 秒这一簇 = 连续两次 3 秒耗尽**（语义判定那一档在一次请求里会串两次调用），说明已经不是偶发。

然后把「到底是 connect 还是 read」这件事**在服务进程内**量死：

| 量什么 | 结果 | 说明 |
|---|---|---|
| `POST /api/admin/settings/test`（23:12 左右，服务进程内） | **30.017 s** 才返回 `{"ok":false,"message":"连不上大模型服务…"}` | **30 秒 = `read` 预算用完**。`read` 超时只在 **connect 成功之后**才可能发生 ⇒ 这一次**握手是真通了**，是**首字节一直没来** |
| 同期 `GET /` | 200，**0.0097 s** | 事件循环没堵 |
| 同期 `GET /api/express` | 200，**0.0104 s** | 不花模型的接口全都正常 |

再加一条决定性的对照（22:52 做的）：**同机、同 key、同地址**，另起一个普通 python 进程、
用**应用自己那个** `DeepSeekClient` 连打 5 次 → **5/5 成功**（1431 / 539 / 664 / 647 / 743 ms）。

⇒ **问题不在网络、不在 Key、不在地址，在那个从 17:22 一直跑到现在（5 小时 40 分）的进程里。**
同一个 bug 因此有**两张脸**：

1. **连的时候握不上手** → `ConnectTimeout` → 刚好 3.0 秒（22:42~23:09 那 12+7 条）
2. **连上了但一个字节都收不到** → `ReadTimeout` → 刚好 30.0 秒（23:12 这次）

第 2 张脸的典型成因是**连接池里囤着上游已经关掉的 keep-alive socket**：
应用把它当活的复用、请求写进一个对端已死的连接，然后一直等首字节等到 `read` 预算烧完。
佐证：`keepalive_expiry=30.0`（`client.py:56`）**比很多边缘节点的空闲关闭时间还长**，
所以"空闲 30 秒后复用"这件事本身就带着踩死连接的概率；而新起的进程池子是空的，
第一次调用一定是新连接 ⇒ 所以它秒通。

⚠️ 诚实交代：`client.py:207` 那行 `print(f"[LLM] 连不上上游 …")` 打在 8000 那个进程的**终端**里，
我拿不到它的 stdout，所以**"哪一条 socket 死了"没法从日志坐实**。
但上面那张表（30.017 s 对 9.7 ms）已经足以把范围钉在"出网连接这一层"，不需要日志也能定修法。

## 一、修法（四处，都在 `app/llm/client.py`）

### 1.1 connect：3.0 → 8.0（两处）

```python
# :53 非流式
timeout=httpx.Timeout(30.0, connect=8.0),

# :311 流式
timeout=httpx.Timeout(60.0, connect=8.0),
```

`read` 的 30 / 60 **一个字不动**。改的只是「多久算连不上」，不是「多久算答不完」。

### 1.2 只在 `ConnectTimeout` 上重试一次（**别的错一律不重试**）

在两处 `except httpx.RequestError` **之前**插一支：

```python
except httpx.ConnectTimeout:
    # 冷连接第一次握手被打断，第二次往往就走已经热起来的那条路。
    # 只重试这一种；auth / 429 / 400 / 地址不合规 重试一万次也是同一个结果，
    # 而且会把「学生等 3 秒」变成「等 16 秒」。
```

实现上建议在**调用点**包一层（`chat` / `chat_stream` 各自一次），不要改 `_get_client()`：

- `_get_client()` 是**按事件循环共享**的（`:37` 起那段长注释），在里面加重试会变成"共享的东西自己重试自己"，语义混乱；
- 重试一次的总代价上限 = `8s × 2 = 16s`，仍在 `read` 预算内，界面上不会出现"永远转圈"。

⚠️ 判据上要钉死：**重试次数 == 1，且只有 `ConnectTimeout` 走这条路**
（变异里会给一条"把重试挪到 `RequestError` 上"的检查，见 §3.3）。

### 1.2-bis（§0.7 那张脸）：`ReadTimeout` 只**在收到 0 字节时**才许重试一次

死连接不只是"握不上手"，还有"握上了但对方从没回一个字"（§0.7 的 30.017 秒）。
这一档必须治，但**只能治一半**：

```python
# 记一个"这轮到底收到过字节没有"的标记：非流式看 resp，流式看有没有解析出任何一行 data:
# 只有「一个字节都没来过」才重试 —— 来了一半再重试，等于把已经生成的内容再付一次钱，
# 而且同一个提案可能被出两张卡。
```

- **非流式**：`httpx.ReadTimeout` 且 `resp` 一个字节没读到时 → 重试一次；
- **流式**：`saw_chunk`（`:301` 那个已有变量）为 **False** 时 → 重试一次；
  `saw_chunk` 已经是 True 的，**绝不重试**。
- 已经进入工具调用循环（发过 proposal）的一律不重试 —— 那是"已经产生副作用"的路径。

判据：`ReadTimeout` 重试的分支里必须能读到 `saw_chunk is False` / `未收到字节` 这个条件，
**且**要有一条"已收到字节 → 不重试"的反控（§3.2-6）。

### 1.4 `keepalive_expiry`：30.0 → 10.0（别在池子里囤上游已经关掉的 socket）

`client.py:56` 现在是 `keepalive_expiry=30.0`。§0.7 的推断链条是：
空闲 30 秒后再复用，而上游边缘节点的空闲关闭时间**没人保证是 60 秒还是 30 秒**
（不同节点不一样，也不写在文档里）⇒ 池里躺着的是"应用以为活着、对端已经关了"的 socket。

把它压到 **10.0**：宁可多握几次手（冷连接实测 0.5~0.9 秒，配合 §1.1 的 8 秒预算是安全的），
也不要在池子里囤死连接。代价是"两次提问间隔超过 10 秒就要重新握手"，
对演示这种一问一答的节奏没有影响（而且这正是 §1.1 放宽 connect 的意义所在）。

⚠️ 这条是**推断性修法**，不是坐实的因果（坐实需要 8000 那个进程的 stdout，见 §0.7 末尾的交代）。
所以它必须配一条**可回滚的观察**：落地后看流水里 `[READ_TIMEOUT]` 是否归零；
如果归零，说明推断对；如果不归零，把它退回去，只留 §1.1~§1.2-bis。

### 1.3 流水里补上「底层到底是哪一种」

`app/data/llm_usage.jsonl` 现在存的是 `LLMError.message`（那句给人看的中文），
所以事后只能看到「连不上大模型服务」六个字，**分不清是 connect 还是 read**——
本单 §0.3 能查出来，靠的是"3.03 秒这个数很特别"，属于运气。

修法：`:207` 那行 `print(...)` 旁边（或 `raise LLMError(...)` 的 message 后面）追加机器标签，
建议只在 `error` 字段里加一个后缀，例如：

```
连不上大模型服务，请检查网络，或到管理控制台确认接口地址是否可用。[CONNECT_TIMEOUT]
连不上大模型服务，请检查网络，或到管理控制台确认接口地址是否可用。[READ_TIMEOUT]
```

`_STUDENT_LLM_WORDS` **不动**（学生看不到这个后缀）；管理端的用量表本来就直接展示 `error` 字段，
管理员一眼能分开这两种。

## 二、判断与理由

### 2.1 为什么不直接把 connect 放到 30 秒（省事）

因为 connect 长了的代价是**学生干等**。8 秒是个折中：实测冷连接 0.5~0.9 秒，8 秒给了 9~16 倍余量——够扛 2~3 次丢包重传（0.2+0.4+0.8+1.6 ≈ 3 秒，正好是现在失败那一簇的位置），
而真的"没网"时学生等 8 秒（+ 重试一次最多 16 秒）也还忍得住；
放到 30 秒就变成"页面上什么都没发生"，那比报错更难解释。

### 2.2 为什么必须加重试，而不能只放宽

放宽只把概率从"经常"降到"偶尔"，**没有消除**。重试一次能把"一次冷连接抖动"这种
**典型的一次性事件**吃掉——第二次几乎必然命中已经热起来的那条路
（同一进程内复用的热连接实测 101~141 ms，比第一次快 5~9 倍）。
两者一起才叫修好了：放宽治"慢"，重试治"断一下"。

### 2.3 为什么错误分类不新增 `kind`

新增 `connect_timeout` / `read_timeout` 两个 kind 就得在 `_STUDENT_LLM_WORDS` 里补两句人话，
而学生**无法据此做任何事**（两种都是"等一下再问"）。
按 `main.py:1853` 那两条纪律（"要加新错就顺手补 kind + 这里补一行"），这里不属于"学生需要区分"的错，
所以只补流水标签，不动话术表。**这是本单唯一一处"少做"的决定，理由写在明面上。**

### 2.4 代价

- 真的断网时，学生等待从 3 秒变成最多 16 秒（8 + 8 重试）。这是本单唯一的体验倒退。
- `test_37:154` 与 `test_47:186` 两条判据钉的是**字符串字面量** `Timeout(30.0, connect=3.0)`，
  改数值必红。这两条本来守的是「超时拆开写、read 是 30 秒」，不是「connect 必须 3 秒」，
  **同单改口**，不是削弱（改法见 §3.1）。

## 五、给执行方的三句

1. **这是"误判"不是"故障"**：网络、Key、地址都好好的。同一个 bug 有两张脸——
