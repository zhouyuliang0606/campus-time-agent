# 57｜知识库检索改写：无 embedding，用「查询前置改写」补语义召回（drop-in）

> 定位：**不改检索算法**，只在入口把学生这句问话扩成检索词，喂给已经存在的 BM25 与条目判据。
> 与 #55 的 `_KB_SPLIT_PROMPT` **不是一件事**：那是入库时把条目 question 拆成 keywords（一次、落库）；本单是查询时改写学生问话（每次、不落库）。
> 前提事实全部现场核对过（2026-10-24，活跃版 `D:/CampusTime`，含 #56）。

## 〇、现场事实（先摆清楚，决定这单只做「改写」不做「换算法」）

| 事实 | 证据 |
|---|---|
| 文档那一路**已经是 BM25 + 字符 bigram**，有分、有排序、有来源配额 | `app/modules/files.py:72`（注释）、`:91 _tokenize`、`:110 _bm25`、`:138 doc_hits`、`:161 pick_diverse` |
| 条目那一路**仍是关键词子串布尔匹配**，不打分不排序 | `app/modules/faq.py:145`（`any(kw and kw in q ...)`）、`:148-152`（编辑距离兜底） |
| 两路共用 `_kb_parts` 这一处出口 | `app/modules/faq.py:127` |
| 硬约束：**没有 Key 也能演示** | `README.md`（"没有 Key 也能演示"）；`run_local.bat` 不依赖模型 |

由此定两条不动的：
1. **不引入 embedding**——会破坏零依赖/离线演示，且不可解释、要额外成本；
2. **不改 `_bm25` 公式、不改 `_kb_parts` 的判据**——只改"喂进去的 query"。

## 一、为什么"只改输入"就够（本单的核心判断）

两路检索都是**把 query 当字符串/词列表吃进去**：

- **文档路**：`doc_hits(query)` 内部 `_tokenize(query)` → BM25。query 多几个同义词，就是多几个检索词。
- **条目路**：判据是 `kw in q`（关键词是不是出现在学生这句话里）。**q 变长了，能命中的条目自然变多**。

所以"补同义/别名"这件事，**不需要动检索代码**，只要在调用 `_kb_parts` 之前把 query 扩写一次。风险面最小，且可回退（删掉调用即回原状）。

## 二、方案：一次便宜的"查询改写器"调用（有 Key 才走）

### 2.1 调用点（唯一一处）

在 `main` 的对话链路里，**`faq` 分支进入 `search_kb` / `answer_for_student` 之前**，先取改写结果；改写失败或没 Key → **原样用原 query**。

> 具体插入行号由执行方按当前 `main.py` 的 faq 分支结构定。本单只钉两件事：**必须在检索之前**、**失败必须回退**。

### 2.2 prompt 正文（新增 `_QUERY_EXPAND_PROMPT`）

```text
你是校园知识库的「检索改写器」。你的唯一任务：把学生的一句问话，改写成适合「字面检索（BM25）」的检索词集合。

铁律（违反即失败）：
1. 只做检索改写，不回答问题、不解释、不寒暄、不输出任何校园事实。
2. 不许臆造学生没提到的楼名、金额、日期、人名、部门；只允许「抽取原句实体」和「补同义/别名」。
3. 输出必须是严格 JSON，不要 markdown 代码块，不要任何多余文字。

改写规则：
A. 原句里的实质词全部保留（它们本来就该被检索到）。
B. 为每个概念补 2~3 个同义/别名，因为检索是按字面重合算分的：
   - 场所：图书馆/自习室/阅览室、宿舍/寝室/公寓、食堂/饭堂、驿站/快递站/取件点
   - 动作：补办/遗失/丢了/怎么办、申请/办理/登记、查询/查看
   - 费用：多少钱/收费/费用/价格/工本费
   - 证件/网络：一卡通/校园卡、学生证、校园网/网络/WiFi
   - 部门：教务/教务处、后勤/后勤处、保卫处/安保
C. 口语可归一到档内更正式的说法（「几点关门」→「开放时间 闭馆时间」），但不得改变语义。
D. 不加无区分度的泛词（「学校」「同学」「请问」这类不许加）。
E. 明显的错别字可归一到正确词（「图收馆」→「图书馆」）；拿不准就别改。

输出 JSON（字段固定）：
{
  "is_campus_fact_query": true 或 false,
  "entities": ["核心名词"],
  "synonyms": ["同义或别名"],
  "expanded_query": "用空格分隔的一串检索词"
}
若 is_campus_fact_query=false（问的是日程/闲聊/情绪/报障），则三个数组/串留空。

示例：
输入：补办学生证多少钱
输出：{"is_campus_fact_query":true,"entities":["学生证","补办","工本费"],"synonyms":["遗失","丢了","学生证补办","收费","费用"],"expanded_query":"补办 学生证 工本费 遗失 丢了 收费 费用"}

输入：图书馆几点关门
输出：{"is_campus_fact_query":true,"entities":["图书馆"],"synonyms":["自习室","阅览室","开放时间","闭馆时间"],"expanded_query":"图书馆 几点 关门 自习室 阅览室 开放时间 闭馆时间"}

输入：我的快递在哪取
输出：{"is_campus_fact_query":true,"entities":["快递","取件"],"synonyms":["驿站","取件点","包裹","取件码"],"expanded_query":"快递 取件 在哪 驿站 取件点 包裹 取件码"}

输入：图收馆在哪个楼
输出：{"is_campus_fact_query":true,"entities":["图书馆"],"synonyms":["自习室","阅览室","位置","在哪"],"expanded_query":"图书馆 在哪个楼 位置 在哪 自习室 阅览室"}

输入：明天上午有什么课
输出：{"is_campus_fact_query":false,"entities":[],"synonyms":[],"expanded_query":""}
```

### 2.3 返回校验（防"模型自由发挥"）

复用 #55 `store.clean_split_words` 的思路，但**不落库**：

- 只取 `expanded_query`；长度上限 = 原句字数 × 2（超了截断，不报错）；
- `is_campus_fact_query != true` → 当作"没扩词"，直接用原 query；
- JSON 解析失败 / 超时 / 非 200 → **静默回退原 query**。

### 2.4 参数、成本与缓存

- `temperature=0`、`max_tokens≈120`、**超时 1.5s**；
- 缓存：按 `query.strip().lower()` 做进程内 LRU（同一句只调一次）；
- 用量记进现有流水，来源标注「内部:检索改写」（与「内部:知识库拆词」同款）。

## 三、必须防的两件事

1. **条目路是布尔匹配，扩词会放宽命中** → 只补"原句实体的同义/别名"，**禁止加泛词**（学校/同学/请问），否则 precision 掉。这是本单最容易出的问题。
2. **日程/闲聊问句不许扩** → `is_campus_fact_query=false` 必须留空，否则「明天有什么课」会被扩成检索词、抢走 planner 的活。

## 四、验证清单

### 4.1 基线（先量，再改）

- 新增 `tests/test_??_kb_query_expand.py`（编号按当时下一个空位）：
  - **A 批**（改写器形状，假模型）：上表 5 条 few-shot 逐条断言 JSON 形状；`false` 那三条必须留空。
  - **B 批**（回退）：模型超时 / 坏 JSON / 无 Key → 检索结果与"完全没有这个功能"逐字相同。
  - **C 批**（召回）：≥20 条「问题 → 期望命中的条目/文档块」，算 hit@1/3。
- **先记录改前基线**，改后同表对比；没有改前那一列，这单就等于没验收。

### 4.2 变异（改坏必须红）

- 去掉「false 时留空」→ 日程问句被扩 → 应红；
- 允许泛词进 expanded → 条目误命中变多 → 应红；
- 超时不回退 → 检索抛错 → 应红；
- expanded 不设长度上限 → query drift → 应红。

## 五、不做的事（写下来免得下一位以为是漏）

1. 不上 embedding、不建向量库（破坏离线演示，见〇）；
2. 不改 `_bm25` / `_tokenize` 的实现（本单是输入侧，不是算法侧）；
3. 不替换 `_kb_fuzzy_hit`（它管错字，本单管同义，两件事）；
4. 不把改写结果落库（每次问一次，存了就是两份真相）；
5. 不在管理端暴露这个能力（学生侧透明即可）。

## 六、可选的下一步（不在本单）

- 若 4.1 的评测显示"语义改写类"仍偏低，再按 `files.py:76` 预留的骨架做 **BM25 召回 + 向量重排**（hybrid），**不是整体替换**；
- 可先做一版**静态同义/别名表**兜底（无 Key 时也能生效一点点），再叠模型改写。

## 七、给执行方的三句

1. 这单**只动输入**：改写 query 再喂现有检索，**不要顺手改 BM25 公式或条目判据**。
2. 一切失败路径必须**静默回退原 query**——改写是增强项，不许变成新的故障点。
3. 先量基线再改，`hit@k` 与"条目误命中"两张表都要有改前/改后。
