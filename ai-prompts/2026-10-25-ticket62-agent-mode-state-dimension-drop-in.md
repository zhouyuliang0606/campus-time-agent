学生明明说了"我自己挑"，却拿不到卡，只能再问一遍。

## A 短路判据加"状态"这一维

### A1. 新增一个纯函数（`main.py`，放在 `_pending_todo_mode` 附近）

```python
def _any_pending(session_id: str) -> bool:
    """这个会话里是否挂着**任何一张**待确认的卡（人话：上一轮有没有留一张让学生点的条）。

    为什么单独立一个函数：它是**状态**判据，被两处判据共用 ——
      ① #62 的 Agent 模式短路（挂着卡时，这句话是在**回应卡片**，不能交给模型）；
      ② #42-A 校历闸 / planner 栏知识库直答闸（挂着卡时不接管，别把学生的卡弄丢）。
    同一件事不许有两个写法：以前 ② 在 `:3210` 就地写了个 `any(...)`，本单把它收成这一份。

    ⚠️ 名单必须**全**。`:929` 的 `_pending_todo_mode`（二选一卡）以前漏在里面，
       于是"只挂着 modality 卡"时两处判据都当没卡 —— 校历闸会把卡挤掉。
       以后 `pending.py` 里每加一种 kind，这里必须跟着加一条，否则就是"卡在但看不见"。
    """
    return any(f(session_id) for f in (
        _pending_todo, _pending_todo_remove, _pending_todo_done,
        _pending_todo_remove_batch, _pending_todo_done_batch, _pending_todo_slots,
        _pending_todo_add_batch, _pending_todo_mode,          # ← 补上的那条
    ))
```

### A2. 短路条件改成两个维度（`main.py:2971`）

```python
        # ★ #61-C Agent 模式：从这里往下全是"替模型抢话"的分支，整段跳掉，直接去找引擎。
        #
        # ★ #62：判据补上"状态"这一维 —— 只看 `_agent_mode` 会连六支**回应卡片/处理材料**的
        #   分支一起关掉（3c-pre / pre2 / pre3 / pre4 与 `_is_material`），而那六支的判据是
        #   `held_*` / `_is_material`（"上一轮留下了什么"），跟学生这句话的措辞无关。
        #   它们的注释里逐条记着掉回模型的实测后果：
        #     「我到底说了它当没听见」「已经帮你排好啦，日程里空的」「连一张确认条都没有」。
        #   所以：**手上有卡、或有待处理的材料 ⇒ 这句话是在回应它 ⇒ 走确定性**；
        #        手上干净 ⇒ 这句话是新的 ⇒ 交给模型，评委才看得见多轮。
        #
        #   代价（说清）：挂着一张卡时，学生若说了句完全无关的闲话，这句也会走快路
        #   （可能被某个分支接走）。可接受 —— 那时候演示的重点已经是那张卡本身了。
        if _agent_mode and not _any_pending(session_id) and not _is_material:
            return await _run_agent_loop(...)      # 参数与原来一字不差
```

**为什么不把 `_holding_card` 提到这里来算**：
`2971` 到 `3210` 之间有几个分支会改写暂存（`3b` 清空、`3c-pre*` 换卡）。
把计算上提，会让 `:3214` 那道闸读到**分支执行前**的状态 —— 那些分支目前都 `return` 了所以看不出差别，
但这属于"靠巧合成立"，不是靠判据成立。⇒ 用 A1 的纯函数**各算各的**，两处各自在自己的正确时刻取数。

## B `test_67` K5 的码页耦合（小而实）

### 现状

`tests/test_67_kb_docs_merged.py:181`

```python
        probe = subprocess.run(
            [sys.executable, "-c", "..."],
            capture_output=True, text=True, cwd=PROJ_DIR, timeout=60)
```

`text=True` 不带 `encoding` ⇒ 按**当前区域设置的码页**解码子进程输出。
中文 Windows 上是 GBK，而子进程里 `print()` 出去的是——
取决于子进程自己的 stdout 编码（同样随区域设置/`PYTHONUTF8` 漂移）。
父进程与子进程两边一旦不对称，就是 `UnicodeDecodeError` 或一串乱码，
`"知识库里没有" in probe.stdout` 直接假红。

**已由 A/B 证明是改动前就存在的**（与 #61 无关）。危害是隐形的：
"跑全量必须带 `PYTHONUTF8=1`"这种依赖不写在任何地方，换台机器、换个 shell 就莫名红一片。

### 修法

```python
        probe = subprocess.run(
            [sys.executable, "-c", "..."],
            capture_output=True, text=True, cwd=PROJ_DIR, timeout=60,
            # 父进程这一侧**写死** utf-8：`text=True` 不带 encoding 就走区域码页，
            # 中文 Windows 上是 GBK，而子进程打出来的是 UTF-8 ⇒ 解码炸/乱码 ⇒ 断言假红。
            # errors="replace" 是第二道：真撞上非 UTF-8 字节时给个替换符继续，
            # 让断言去比内容，而不是让整个文件在解码这一步就崩。
            encoding="utf-8", errors="replace")
```

**顺带查一遍同类**（本单只报不改，除非同文件里还有）：
`grep -rn "text=True" tests/ | grep -v encoding` —— 有就记进回报，**别一次性全改**，
一次改一处才分得清是谁红的。

## 给执行方的三句

1. **判据加的是"状态"不是"词表"**。别去列「我自己挑 / 你帮我定 / 改成七点」这些词——
   那会变成第二份语义判词表，漏一个词就漏一条红线。`_any_pending()` 探的是会话里有没有卡，
   跟学生怎么说完全无关，这才是它该长的样子。
2. **`_holding_card` 漏 `_pending_todo_mode` 是开工前就存在的**，不是 #61 引入的。
   修的时候两边（`:3210` 与新的短路点）**共用 A1 那一个函数**，不要在 A2 里再写一遍 `any(...)`
   ——那是这个项目已经赔过两次的东西。
3. **W5 有可能不红**。真不红就回来报"本机不复现"，别为了让它红去改 `PYTHONUTF8` 或改断言——
   测试的目的是钉住真因，不是钉住红色的出现。
