# 21 · 提案摆在那儿，回确认却反问时间

> 报障是**两张截图**，没有文字。这是同一件事的**第四次**报障
> （前三次见 `ai-logs/18`、`19`、`20`），症状还是"吹了一系列、最后没弹确认条"，
> 可四个断点里**有三个**跟前三次一点关系都没有。

## 一、两幕

**图 1**——提案写得规规矩矩，学生一个字不差地照着回：

```
管家： 好，那就定 **周一 07:00~08:00 健身**。

       跟你确认一下这条待办：
       - 名称：健身
       - 时间：周一 07:00~08:00

       回我一句「确认添加」，我就帮你加上。
我：   确认添加
管家： 把想安排的时间和日期说一下吧，我算好给你出确认条，你点头我才写进日程。
       · 缺时间就说「几点到几点」，比如「下午两点到三点」；
       · 缺日期就说「哪一条」，比如「周二」「明天」。
```

任务名、日期、时段**三样全在**，还手把手教了他怎么回。他照做了。
然后被问："你到底想安排在什么时候？"

**图 2**——"健身"说了两遍，系统始终只问时间：

```
管家： 我在呢，想安排什么事、定在哪天，你说一声就行～
我：   我要去健身，帮我安排个时间
管家： 需要我帮你安排到具体时间吗？你先说下想安排在哪一天吧
我：   你帮我安排
管家： 把想安排的时间和日期说一下吧……
```

原地打转。

顺带一个线索：那句「把想安排的时间和日期说一下吧」**不在代码里**
（全项目搜不到，只在 `ai-logs` 和测试断言里出现过）→ 它是**大模型自己生成的**。
也就是说这一幕走的是配了密钥的真模型路径，请求从确定性分支一路漏到了模型手上。

## 二、四个断点

### 断点 ①：`_REPLY_TASK_RE` 不认「名称：」

`parse_todo_from_reply` 有两档：固定格式（准）→ 散文式（松，且要求它自称发过提案）。
固定格式那一条长这样：

```python
r"(?:任务|事项|标题|安排)\s*[：:]\s*([^\n，,。；;：:｜|\-—]{1,30})"
```

管家这次写的是 **「- 名称：健身」**——**不在这四个词里**。
于是整份规规矩矩的方案掉出第一档，只能退给第二档的散文抠法抠任务名。

### 断点 ②：Markdown 的星号跟着名字一起进了门

退到散文抠法之后，抠出来的是 `健身**`——卡片上就印着
「要不要把 **健身\*\*** 排进日程？」（截图里任务名后面那两个星号就是这么来的）。

补了两个地方，因为这一琐 Parker 星号有**两种**贴法：

```python
# 「**周一 07:00~08:00 健身**」—— 星号包住整段
# 「07:00~08:00 **健身**」   —— 星号紧贴名字
_TITLE_AFTER_SPAN_RE = re.compile(
    r"\d{1,2}:\d{2}\s*(?:到|至|-|~|～)\s*\d{1,2}:\d{2}[\s*`_]*"   # 先啃掉排版符号
    r"([^（）()「」『』《>》“”\"'，,。；;：:｜|、*`_\s\n]{2,12})")     # 名字本身不许含
```

第一处：给 `_REPLY_TASK_RE` 补上「名称」，名字过一遍 `_clean_reply_name`
（引号和 `*`_~` 放一个集合里 strip，让它反复剥，因为可能交替嵌套成 `**「健身」**`）。
让这份规规矩矩的方案**留在固定格式那一档**——那是它本来就配得上的待遇。
第二处：`_clean_prose_title` 也要剥，因为散文的三条路都从那儿出。

### 断点 ③：`_pick_title` 把一句话粘成了一团（图 2 的根因）

擦噪声的最后两步是：**把逗号换成空格，紧接着又把空格全删掉**。

```
「我要去健身，帮我安排个时间」
  → 「我要去健身」+「帮我安排个时间」
  → 粘成「去健身帮我个时间」
  → 判真看见"帮我"（语气词，不是事名的一部分）→ 整句否掉 → 返回"待办"
  → 系统回他「好——**要安排的是什么事**？」
```

他第一句就说了"健身"。

修法是加**切段重试**：整句擦完判不过真，就**按标点切成一句句再擦一遍**。
一段话脏，不该拖累另一段：

```python
    whole = _strip_title_noise(t)
    if _title_ok(whole):
        return whole
    for piece in re.split(r"[，,。！!？?；;：:\n]+", t):
        cand = _strip_title_noise(piece)
        if _title_ok(cand):
            return cand
    return "待办"
```

手测：`我要去健身，帮我安排个时间` → `健身`。
副作用也确认过：`去角质`→`角质`、`加油打卡`→`油打卡`——**与改动前一致**，不是新回归。

### 断点 ④：一道挡得太宽的闸门（图 1 的根因）

3a-c「确认落空」这条兜底，要把管家那份方案从会话历史里捞回来重新挂条。
它外面套着一道防重复写的闸门：

```python
if proposal is None and not already_written:    # ← 老写法
```

`already_written` 问的是"**最近这几轮有没有真的写过库**"。
只要附近出现过一次「已加入日程」，往后哪怕管家又给了一份干净方案、
学生老老实实回一句「确认添加」，也**一个字都捞不回来** → 掉到 3c →
‼️ 反问他「好——**要安排的是什么事**？」。

对着一份已经写好的提案问"要做什么"，这就是截图那一幕。

## 三、这道闸门我改错了两次

改这道闸门的过程本身，比结论更值得记下来。三版问的是**三个不同的问题**：

| 版本 | 问的是什么 | 结果 |
| --- | --- | --- |
| 老版本 | 最近这几轮有没有写过库（**整段**挡掉） | ❌ 太粗。写过一次之后，新方案永远捞不回来（图 1） |
| 第一版 | 这句话是不是系统自己写的账（跳过回执句） | ❌ 粒度对了，**漏了后半截**：提案自己也会过期 |
| 最终版 | **这场商量是不是还没落地** | ✅ |

第一版写出来的时候，两条报障全都绿了、全量也过了——**直到全量跑出一条挂**：

```
❌ 写成功之后，再回「好的」不会又挂出一条
```

（第六批那条断言，锁的是第六批末尾那一幕：管家写方案 → 回「可以」补条 →
回「确认」**真写库** → 回「好的」不许再挂。）

我被桑以为"跳过回执句就够了"，可那份提案虽然**已经被学生点完、库都写好了**，
**它的文字照样留在历史里**。只跳过回执、不划一条起跑线，就会把这份早已落实过的
旧提案重新捞出来挂一遍。

所以正解是**划一条起跑线**：找到最近一次写库回执的位置，只在它**之后**找方案。

```python
receipt_at = [i for i, m in enumerate(recent_msgs)
              if m.get("role") == "assistant"
              and any(k in (m.get("content") or "") for k in _WRITTEN_RECEIPTS)]
started = (receipt_at[-1] + 1) if receipt_at else 0
for m in reversed(recent_msgs[started:]):
```

回执之前的提案，在这一幕之前已经执行过了，不许翻回去；
回执**之后**给的新方案，照样照挂（这一条塌了就退回第一版的毛病）。

> **教训** — 这跟 `ai-logs/20` 记的是同一件事的两种形态：
> **症状相同 ≠ 原因相同**，反过来也成立——
> **同一个抽象的两种表达，保不齐一个是另一个的特例**。
> "跳过回执句"看着像"划起跑线"的简化版，其实它漏掉的是完全不同的东西。
> 而这道闸门的护栏**早就有人在守**（第六批那条断言）——
> 全量跑一次就把它抓出来了。这也是为什么每次收尾都得把全量跑完再提交。

## 四、另一个新发现：探针也可能验证不了你想验的东西

排查时我给反向场景（"写完库回一句好的"）补了个探针场景，结果它出的是
三张**标题叫「好的」**的候选卡、`kind` 是 `None`、`trace` 是空的——
哪个都对不上我改的那段。

查下来根子在 `app/main.py` 第 1483 行：

```python
if module_key == "planner" and not get_llm_config()["api_key"]:
    result = mock_planner(message, history, persona_key)
    return {..., "trace": []}      # ← 离线 Mock，trace 就是空的
```

沙箱里没有 `settings.json` → 没配密钥 → **`planner` 模块的请求根本走不到 `AgentEngine`**，
连我注入的假引擎都碰不着。探针想验确定性分支，实际验的是离线 Mock。

判据（一眼识破用）：**`trace` 是空的 + `options` 里没有 `kind`** = 走了 Mock。
确定性分支的每一条返回都写着自己的 `phase`。

## 五、顺手发现、但**这次没修**的一笔

上面那条岔路挖出了一个真毛病，条件是"**离线演示（没配密钥）+ 学生在 planner 里随口应答**"：

```
学生加完待办 → 回一句「好的」
→ mock_planner 的第 4 步（无条件兜底：查空档、摊最多 3 段）
→ 三张候选卡，每张的 title 都用 `_guess_title("好的")` = 「好的」
```

`mock_planner` 那一档只在消息含「日期 起-止」时才算真办理，其余一律摊候选，
**中间没问过"这句话像不像一件要做的事"**。

这次没动它，因为：
1. 它跟用户报的不是同一处——**用户那台机器配了密钥**，走的是真模型；
2. 要拦住「好的/收到/谢谢/ok」得引 `is_confirmation`（跨模块，有循环 import 风险），
   还得给三份性格各加一句 idle 措辞——动静比这次修的三处加起来还大；
3. Mock 这条路径几乎没有断言守着，贸然改的风险收益不合适。

留在脑子里的一条：第十四批那条反向断言的判据因此只锁 `todo_add`
（这条护栏本来管的就是"不许重复挂待办确认条"），并在断言名旁边的注释里点明了这一点
——**测试不许为了变绿而悄悄拓宽判据**。
