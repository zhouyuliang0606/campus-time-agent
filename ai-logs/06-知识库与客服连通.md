# ai-log 06 · 把模块连起来（知识库 + 客服人格）

> 开发日记第 6 篇：从"四个各自为战的模块"走到"三层互通的一个系统"。
> 对应你的原话：**"把几个模块连起来，搭建知识库，配置客服"**。

## 一、需求拆成三件事

| 你的话 | 落到代码上 | 做完的样子 |
| --- | --- | --- |
| 把几个模块连起来 | 一个引擎 + 一个注册表 + 一份数据，多端复用 | 学生/驿站/管理员共用同一套引擎、同一份台账 |
| 搭建知识库 | 管理台能零代码增删改问答，学生端问答直接吃它 | 管理员后台加一条，学生端立刻能答 |
| 配置客服 | 客服人设可配，驿站端对话实时用它 | 改个语气，AI 客服立刻换个人说话 |

## 二、第一步：存储层掏出"知识库 + 人格"（app/store.py）

原来 `store.py` 只有两张表（学生消息、通知）。现在补了两组读写：

| 函数 | 人话 |
| --- | --- |
| `list_kb()` | 列出知识库全部条目 |
| `add_kb_entry(q, a, keywords)` | 加一条问答 |
| `update_kb_entry(i, q, a, keywords)` | 按序号改 |
| `delete_kb_entry(i)` | 按序号删 |
| `get_persona()` | 读当前客服人格（没有就用默认值） |
| `set_persona(name, role, tone, rules)` | 存客服人格 |

`DEFAULT_PERSONA` 里放了一套默认人设（名字"小园"、邻家学姐语气），
管理员从没配过时也能正常演示。

## 三、第二步：新模块 station.py —— 这里有两个设计亮点

### 亮点 1：系统提示写成了"函数"，而不是字符串

普通模块的系统提示是一句死的字符串；station 的是 `build_system_prompt()`，
**每次对话都会重新读一遍 `persona.json`**。

为什么？因为管理员随时可能在后台改人设。
写成函数，改完**下一条对话就生效，不用重启服务**——这是"配置客服"能落地的关键。

`main.py` 里配合加了一行判断：

```python
prompt = prompt_src() if callable(prompt_src) else prompt_src
```

意思是：登记在表里的提示如果是"能调用的函数"就调用它，否则当普通字符串用。
这样以后再加需要动态拼装的模块，不用改引擎。

### 亮点 2：工具直接复用快递模块的函数

```python
from app.modules.express import get_by_code, list_pending_pickup
```

驿站客服用的就是学生端查快递的那份台账（`express.json`），只是立场不同：
- 学生端问"**我的**快递到哪了"
- 驿站端用它**答复咨询 + 主动推送取件提醒/滞留预警**

这正是你说的"几个模块连起来"——不是复制一份数据，是共用一份。

## 四、第三步：后端接口（app/main.py）

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/admin/kb` | 列出知识库 |
| POST | `/api/admin/kb` | 新增条目（关键词按逗号拆） |
| PUT | `/api/admin/kb/{index}` | 修改第 N 条 |
| DELETE | `/api/admin/kb/{index}` | 删除第 N 条 |
| GET | `/api/persona` | 读客服人格 |
| POST | `/api/persona` | 存客服人格 |
| GET | `/station` | 驿站端页面 |

越界的增删改都返回 404，空问题空答案返回 400——这些边界在冒烟测试里都验过了。

## 五、第四步：管理台 UI（app/static/admin.html）

从"两栏"扩成"四块"：
1. 📢 发布通知
2. 🎭 **客服人格配置**：名字 / 角色 / 语气 / 准则，保存即写 `persona.json`
3. 📚 **知识库管理**：右边列表 + 左边表单，编辑/删除即时生效
4. 📥 学生消息收件箱（5 秒轮询）

目标是让完全不懂代码的管理员，靠这个页面就能维护整套知识库和客服人设。

## 六、第五步：驿站端页面 + 登录三种身份

- 新建 `app/static/station.html`：顶部展示当前客服人格（带"去管理控制台改人设"的跳转），
  五个快捷操作（列待取/写取件提醒/滞留预警/查取件码/自我介绍），对话固定带 `module:"station"`
- `login.html` 从两个身份扩成三个：学生 / 管理员 / **驿站商户**

## 七、一个值得记一笔的取舍：哪些数据入库？

| 文件 | 入库？ | 理由 |
| --- | --- | --- |
| `kb.json` | ✅ 入库 | 它是"种子知识库内容"，本身就是作品的一部分，值得版本管理。管理员改了会出现 diff，这是知识内容的变更历史 |
| `persona.json` | ❌ 不入库 | 它是管理员在后台配出来的**运行时数据**。默认值由 `store.py` 的 `DEFAULT_PERSONA` 兜底，删了也能自动恢复 |
| `student_messages.json` / `notices.json` | ❌ 不入库 | 同上，运行时产生的 |

判断标准就一句：**它是"内容"还是"状态"？** 内容入库（可版本化、可评审），状态不入库（每人跑出来不一样）。

## 八、验证：手工冒烟 23 项全过

用 FastAPI 的 TestClient 跑了一遍不需要大模型密钥的纯接口：

```
=== 1. 健康检查与页面路由 === 6 项全过（含 station 模块已注册、四个页面都能打开）
=== 2. 知识库读取 === 10 条
=== 3. 知识库增删改 (CRUD) === 8 项全过
   ✅ 新增 / 关键词按逗号拆分 / 空问题被拒 / 修改 / 越界 404 / 删除 / 越界 404 / 条目数还原
=== 4. 客服人格配置 === 4 项全过（含空名字回退默认值）
=== 5. 旧接口回归 === 4 项全过
===== 通过 23 项，失败 0 项 =====
```

做测试时特意**先把 `kb.json` 备份、跑完再还原**，
因为 CRUD 会重写文件（格式可能变动），不还原就会污染被 git 跟踪的种子数据。

## 九、现在的三层闭环

```
管理台 /admin ──写──→ kb.json ──读──→ 学生端「校园问答」
             ──写──→ persona.json ──读──→ 驿站端「AI 客服」
 round-trip： Admin 改 → 立即生效 → 学生/驿站端能用
```

学生每轮对话还会自动上报到管理员收件箱，管理员知道同学们在关心什么，
再回头补知识库——这就形成了一个能自我完善的小循环。

## 十、踩坑一个：无 Key 时接口返回裸 500（已修）

打通之后真机跑了一遍，发现一个演示现场会很难看的问题：

| 项 | 内容 |
| --- | --- |
| **现象** | 没配 `DEEPSEEK_API_KEY` 时问一句，`/api/chat` 直接 `Internal Server Error` |
| **根因** | `client.py` 里 `resp.raise_for_status()` 收到 401 抛异常 → `engine` 没 catch → `main.py` 没兜底 → 异常一路冒到 FastAPI 变成 500 |
| **为什么必须修** | `config.py` 自己承诺过"没有 Key 时返回友好错误，不会崩溃"，说了却没做到；而评委机器上 Key 没配好是大概率事件 |
| **改法** | ① `client.py` 新增 `LLMError` 统一错误类型，并按状态码翻译成人话（401=Key 无效、429=限流、网络异常）；② `main.py` 的 `/api/chat` 接住异常，把原因塞进 `answer` 和 `trace` |
| **现在的效果** | 页面上出现的是「⚠️ 还没配置大模型密钥：请把 .env.example 复制成 .env…」，照着做就行 |

**教训**：自己写的那句"承诺"（注释/提示文案）要回头验证是不是真的实现了，
尤其是"异常分支"——正常流程跑得通不代表出错时也体面。
